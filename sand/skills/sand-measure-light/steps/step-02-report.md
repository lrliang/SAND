# Step 2: 认知失调报告

## MANDATORY EXECUTION RULES (READ FIRST):

1. 读完整个步骤文件后再执行——不要边读边做
2. 按编号顺序执行每个子节——不跳步
3. 遇到不确定性时请求人类确认——不猜测用户意图
4. 每个子节完成后向用户汇报进度——保持透明
5. 失败时快速报错并说明原因——不静默降级或继续

## YOUR TASK:

基于 step-01 采集的度量数据，生成数据驱动的认知失调报告——用正向/负向指标对比、趋势分析和改善建议，驱动团队渐进变革。

## EXECUTION SEQUENCE:

### §1 加载度量数据

1. **读取最新度量文件**：扫描 `.sand/metrics/` 目录，按文件名排序找到最新的 `*_metrics.json`
   - 如果未找到 → `❌ 未找到度量数据。请先运行 Step 1 信号采集。` → **HALT**

2. **读取历史数据**（可选）：扫描 `.sand/metrics/` 中所有 `*_metrics.json` 文件
   - 如果仅有 1 个文件 → 标注"首次采集，无趋势数据"
   - 如果有 2+ 个文件 → 加载最近 5 轮数据用于趋势分析

3. **展示加载状态**：
```
📊 度量数据加载

当前数据：{current_date}_metrics.json
历史轮次：{history_count} 轮（{first_date} — {last_date}）
可用信号：{available_count}/5（{unavailable_list}）
```

### §2 信号分类

将 5 个信号按 DORA 基准和健康范围分为正向和负向：

**分类规则（无历史数据时）：**

| 信号 | 正向条件 | 负向条件 |
|------|---------|---------|
| PR 周期时间 | ≤ 团队历史中位数或 ≤ 48 小时 | 持续增长或 > 168 小时（1 周） |
| 事故标签 | ai_related 占比 ≤ 30% 或为 0 | ai_related 占比 > 50% |
| AI 参与度 | 10%-70%（有 AI 参与且未过度依赖） | < 5%（闲置）或 > 80%（过度依赖） |
| 变更失败率 | DORA Elite/High（≤ 15%） | DORA Low（> 30%） |
| 部署频率 | DORA Elite/High（≥ 每周） | DORA Low（< 每月） |

**分类规则（有历史数据时）：**
- 正向 = 与前一轮相比改善（值向健康方向移动）
- 负向 = 与前一轮相比恶化（值偏离健康方向）
- 持平 = 变化幅度 < 5%

对 unavailable 的信号标记为"数据缺失"，不参与分类。

### §3 趋势分析

如有 2+ 轮历史数据：

1. 计算每个信号的**变化方向**（↑ 上升 / ↓ 下降 / → 持平）和**变化幅度**（百分比）
2. 标注**显著变化**：幅度 > 10% 的信号加重标记
3. 生成趋势表：

```
📈 趋势分析（最近 {N} 轮）

| 信号 | 当前值 | 上轮值 | 变化 | 方向 | 判定 |
|------|--------|--------|------|------|------|
| PR 周期时间 | {cur} 小时 | {prev} 小时 | {delta}% | ↑/↓/→ | 正向/负向/持平 |
| ... | ... | ... | ... | ... | ... |
```

如仅有 1 轮数据：
```
ℹ️ 首次采集，无趋势数据。下次运行将展示变化趋势。
```

### §4 认知失调叙事

这是报告的核心价值——生成 2-3 条"好消息 vs 坏消息"对比叙事，突出团队自我感觉与数据之间的落差。

**叙事生成规则：**

1. 从正向信号和负向信号中各取 1-2 个，构成对比对
2. 使用"X 是好消息，但 Y 需要注意"的句式
3. 用具体数字支撑（不使用模糊表述）
4. 引用团队可能的自我感觉作为对照

**叙事模板（参照 PRD §Journey 4 吴芳）：**

- **产量 vs 质量模式**：
  > "团队的部署频率达到每周 {N} 次（DORA {Level}），交付节奏令人印象深刻。但变更失败率为 {M}%（DORA {Level}），意味着每 {K} 次部署中就有 1 次导致问题——快速交付正在积累风险。"

- **AI 采纳 vs 审查模式**：
  > "AI 参与度为 {N}%，说明团队已经深度融入 AI 协作。但 PR 周期时间从 {prev} 小时增长到 {cur} 小时——AI 加速了代码生产，审查流程却成了瓶颈。"

- **事故归因模式**：
  > "过去 {days} 天共 {total} 次生产事故，其中 {ai_count} 次（{ratio}%）的根因是 AI 生成的代码。三通道验证可能需要加强对 AI 输出的专项检查。"

如全部信号为 unavailable，生成"数据缺失"叙事：
> "本次采集中 {N} 个信号无法获取。度量的价值在于持续追踪——建议先从 Git 信号开始（仅需 Git 仓库），逐步补充 CI 数据。"

### §5 推荐行动

基于负向信号推荐具体的改善行动，关联到 SAND Skill：

| 负向信号 | 推荐行动 | 关联 Skill |
|---------|---------|-----------|
| PR 周期时间过长 | 引入三通道验证减轻人工审查负担 | `sand-validate-delivery` |
| 变更失败率过高 | 加强执行契约的 must_pass 条目覆盖 | `sand-create-intent` → `sand-validate-delivery` |
| AI 相关事故比例高 | 在 Validate 阶段增加 AI 输出专项检查 | `sand-validate-delivery` |
| AI 参与度过低 | 运行成熟度评估定位采纳瓶颈 | `sand-assess-maturity` |
| AI 参与度过高 | 运行复盘检查认知债务风险 | `sand-run-retrospective` |
| 部署频率过低 | 评估编排效率和 CI/CD 流程 | `sand-design-orchestration` |

对 unavailable 的信号：推荐补充数据采集方式（CI API 配置或 CSV 定期导出）。

生成 Markdown 格式的认知失调报告：

**报告结构：**
```markdown

**生成时间：** {datetime}
**数据来源：** {git_repo}
**度量窗口：** 最近 {days} 天

## 信号概览

| 信号 | 值 | 状态 | 判定 |
|------|-----|------|------|
| ... | ... | ... | ... |

## 趋势分析

{趋势表或"首次采集"说明}

## 认知失调发现

{2-3 条对比叙事}

## 推荐行动

{按优先级排列的改善建议}

---
```

**展示完整报告内容给用户。**

❌ 全部 5 个信号 unavailable → 生成"数据缺失"报告（不 HALT），建议补充数据源
