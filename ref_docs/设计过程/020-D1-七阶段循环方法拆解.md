# D1：SDC 七阶段循环方法拆解

[Framework DNA #7]：SAND Development Cycle (SDC) — 完整定义
Concept：SDC 是 SAND 的核心方法引擎，类比 TOGAF ADM。每个阶段都有标准化的输入、活动、输出、角色分工和 AI 参与方式。7个阶段 + 治理中心轴形成闭环，每一圈产生可复用的 AI 资产，使下一圈更高效
Novelty：与 ADM 的关键区别——SDC 的循环不是单一节奏的，每个阶段的"转速"不同。Intent 可能几小时完成，Build 可能几分钟（AI 生成），Validate 可能需要几天（人类深度审查）。这是 AI 原生开发特有的"非均匀节奏"

我用一个统一的结构来拆解每个阶段：

---

## 阶段 A：Assess（评估）

> "我们在哪里？我们准备好了吗？"

| 维度 | 定义 |
|------|------|
| 核心目标 | 评估当前 AI 成熟度，识别转型机会和差距 |
| 输入 | 组织现状数据、前一轮 Learn 阶段的反馈、外部 AI 能力演进情报 |
| 关键活动 | 成熟度自评（L1-L5模型）、AI 能力差距分析、团队准备度检查、工具平台健康度评估 |
| 输出/工件 | 《AI 成熟度评估报告》、《转型机会矩阵》、《本轮改进计划》 |
| 人类职责 | 问题域负责人定义评估范围，变革催化师组织评估活动 |
| AI 职责 | 自动化采集度量数据、生成对比基准分析、辅助差距可视化 |
| 治理检查点 | 评估结论需经管理层确认，改进计划需获得投资授权 |

这个阶段的独特性：它既是循环的起点也是终点。第一次运行时，这是"组织诊断"；后续每轮运行时，它变成"上一轮学习成果的吸收 + 下一轮目标的校准"。

[Framework DNA #8]：Assess 阶段的双模运行
Concept：Assess 有两种模式——"首次诊断模式"（全面组织评估，可能需要2-4周）和"循环校准模式"（基于上轮 Learn 的快速检查，可能1-2天）。这解决了 TOGAF ADM 中 Preliminary Phase 与 Architecture Change Management 割裂的问题
Novelty：同一个阶段，两种节奏——这是 AI 原生框架"自适应节奏"的第一个体现

---

## 阶段 B：Intent（意图）

> "我们要解决什么问题？成功长什么样？"

| 维度 | 定义 |
|------|------|
| 核心目标 | 将模糊的业务需求转化为结构化的意图声明和执行契约 |
| 输入 | Assess 阶段产出的改进计划、业务目标、用户/市场信号 |
| 关键活动 | 意图建模（Intent Modeling）、验收契约定义、约束边界划定、投资假设声明 |
| 输出/工件 | 《意图声明》（Intent Statement）、《执行契约》（Execution Contract）、《约束上下文》（Constraint Context）、《投资假设》（Investment Hypothesis） |
| 人类职责 | 问题域负责人定义"为什么做"和"成功标准"，FDE+ 参与可行性判断 |
| AI 职责 | 辅助需求澄清和歧义消除、自动生成可行性草图、检索相似意图模式供参考 |
| 治理检查点 | 意图对齐评审——确认意图声明与组织战略一致，投资假设获批 |

[Framework DNA #9]：意图声明的标准化模板
Concept：每个意图声明必须包含5个必填字段——(1) 业务目的（Why）、(2) 期望成果（What）、(3) 验收标准（How to verify）、(4) 约束边界（What NOT to do）、(5) 上下文引用（Related knowledge）。这不是自然语言叙述，而是结构化的、AI 可解析的格式
Novelty：传统 User Story 是"As a... I want... So that..."的叙事格式，意图声明是面向人-AI协作优化的结构化格式——它同时服务于人类理解和 AI 执行

---

## 阶段 C：Orchestrate（编排）

> "谁来做？怎么协作？AI 拓扑怎么设计？"

| 维度 | 定义 |
|------|------|
| 核心目标 | 为意图设计最优的人-AI协作方案和 Agent 拓扑 |
| 输入 | 意图声明、执行契约、可用 AI 能力清单、团队能力画像 |
| 关键活动 | Agent 拓扑设计（单Agent/多Agent/人机混合）、上下文策略制定、工作流编排、人类审查点设置 |
| 输出/工件 | 《编排方案》（Orchestration Plan）、《Agent 拓扑图》、《上下文策略》、《人类介入点定义》 |
| 人类职责 | AI 编排师设计整体方案，FDE+ 确认技术可行性和审查点位置 |
| AI 职责 | 推荐 Agent 组合、评估上下文完整度、识别潜在的编排风险 |
| 治理检查点 | 编排方案评审——特别审查人类介入点是否充分、数据安全边界是否合规 |

[Framework DNA #10]：编排阶段是 SAND 最独特的阶段
Concept：这个阶段在传统框架中完全不存在。SAFe 没有"编排"，TOGAF 没有"编排"，Scrum 更没有。它是 AI 原生开发独有的——你需要决定"哪些 AI 做什么、人在哪里介入、上下文怎么流转"。这是 SAND 区别于所有现有框架的核心创新点
Novelty：Orchestrate 阶段的产出决定了整个 Build 阶段的效率。一个好的编排方案可以让 AI 杠杆率达到10x，一个差的编排可能让 AI 成为阻碍。这是"AI原生工程"最核心的能力

[Framework DNA #11]：Agent 拓扑模式库
Concept：SAND 应该预定义几种标准的 Agent 拓扑模式——
- Solo：单 Agent + 单 FDE+，适合低复杂度任务
- Pipeline：多 Agent 串行流水线，适合标准化交付流程
- Swarm：多 Agent 并行探索 + 人类仲裁，适合探索性问题
- Hierarchy：分层 Agent 团队 + 人类指挥官，适合大型系统构建
Novelty：这类似于软件架构模式（MVC/微服务/事件驱动），但用于人-AI协作架构

---

## 阶段 D：Build（构建）

> "AI 生成，人类审查，协作构建"

| 维度 | 定义 |
|------|------|
| 核心目标 | 在编排方案指导下，AI 生成 + 人类审查的协作构建 |
| 输入 | 编排方案、意图声明、执行契约、上下文资产 |
| 关键活动 | AI 驱动代码/文档/测试生成、人类审查门禁、迭代精炼、架构符合性检查 |
| 输出/工件 | 可工作软件增量、测试套件、技术文档、架构决策记录（ADR） |
| 人类职责 | FDE+ 审查 AI 产出，判定"接受/优化/重定向"，处理例外情况 |
| AI 职责 | 代码生成、测试生成、文档生成、自动化安全扫描 |
| 治理检查点 | 代码审查（包含 AI 生成代码的专项检查）、架构符合性验证 |

[Framework DNA #12]：Build 阶段的"非均匀时间"特性
Concept：Build 是循环中最具"AI加速"效应的阶段。AI 可能在几分钟内生成传统需要几天的代码量，但人类审查时间不会等比压缩——这导致"Build 阶段的瓶颈从生产转移到审查"。SAND 需要在 Build 阶段内建"审查节奏管理"机制
Novelty：传统框架假设"构建=最耗时的阶段"，SAND 假设"构建=最快但审查最关键的阶段"

---

## 阶段 E：Validate（验证）

> "达标了吗？安全吗？合规吗？"

| 维度 | 定义 |
|------|------|
| 核心目标 | 基于执行契约的系统性验证，确保 Build 产出满足意图 |
| 输入 | Build 产出物、执行契约、质量标准、合规要求 |
| 关键活动 | 执行契约验证（自动化+人工）、质量门禁检查、安全扫描、合规审计、性能验证 |
| 输出/工件 | 《验证报告》、《质量门禁决策》（通过/有条件通过/打回）、《安全合规审计报告》 |
| 人类职责 | FDE+ 做最终的验收判断，安全/合规团队做专项审查 |
| AI 职责 | 自动化测试执行、安全漏洞扫描、合规规则检查、覆盖率分析 |
| 治理检查点 | 质量门禁决策会议——决定产出是否可进入 Operate，还是需要回退到 Build |

[Framework DNA #13]：Validate 的回路设计
Concept：Validate 不是单向通过的，它有三条出路——(1) 通过→进入 Operate、(2) 小问题→回退到 Build 微调、(3) 意图偏差→回退到 Intent 重新定义。这三条回路使循环具有自修复能力
Novelty：TOGAF ADM 的阶段也有回路，但 SAND 的回路是"有代价的"——每次回退都会记录为一个"意图偏差事件"，用于 Learn 阶段分析

---

## 阶段 F：Operate（运营）

> "上线、监控、持续优化"

| 维度 | 定义 |
|------|------|
| 核心目标 | 安全部署、实时监控、AI 辅助运营优化 |
| 输入 | 通过验证的交付物、部署策略、监控配置 |
| 关键活动 | 自动化部署、运行时监控、异常检测与告警、性能优化、事故响应 |
| 输出/工件 | 运行中的系统、监控仪表盘、Runbook、事故报告、运营优化建议 |
| 人类职责 | 设定运营目标和 SLA、处理 AI 无法解决的异常、做升级/降级决策 |
| AI 职责 | 自动化部署流水线、异常检测、根因分析、自动扩缩容建议 |
| 治理检查点 | 运营健康检查（定期）、SLA 合规审查、安全事件响应审计 |

---

## 阶段 G：Learn（学习）

> "我们学到了什么？什么可以资产化？"

| 维度 | 定义 |
|------|------|
| 核心目标 | 从整个循环中提取经验，将可复用知识转化为 AI 资产 |
| 输入 | 全循环产出的数据——意图偏差记录、审查日志、运营数据、团队反馈 |
| 关键活动 | AI 复盘（Blame-free AI Retrospective）、意图模式提炼、上下文资产沉淀、度量指标分析、最佳实践编目 |
| 输出/工件 | 《循环复盘报告》、新增上下文资产、意图模式库更新、度量趋势分析、《下一轮改进建议》 |
| 人类职责 | 变革催化师引导复盘，全角色参与经验分享和反思 |
| AI 职责 | 自动化数据汇总分析、模式识别、建议资产化候选项 |
| 治理检查点 | 学习成果需被验证后才纳入组织知识库（防止错误经验污染） |

[Framework DNA #14]：Learn → Assess 的飞轮效应
Concept：Learn 阶段的核心产出不是"报告"，而是AI 资产——可复用的上下文库、经过验证的意图模式、优化后的 Agent 拓扑配置。这些资产直接反馈到下一轮 Assess（降低评估成本）和 Orchestrate（提高编排效率），形成越转越快的飞轮
Novelty：传统框架的"回顾/复盘"产出的是"行动项"（Action Items），SAND 的 Learn 产出的是"可执行资产"——这才是 AI 原生的学习方式

---

## 中心轴：Governance（治理）

> "贯穿全程的人类决策权和审计链"

[Framework DNA #15]：治理不是阶段，是中心轴
Concept：治理贯穿 SDC 的所有7个阶段，不是某个阶段的工作。它包含四根支柱——
1. 决策治理：关键决策点的人类最终确认权（Human-in-the-Loop）
2. 合规治理：AI 使用边界、数据安全、开源许可证合规
3. 质量治理：AI 产出的审查覆盖率、质量门禁标准
4. 审计治理：所有 AI 参与的决策和产出必须留下可追溯的证据链
Novelty：治理是 SAND 方法循环的"旋转轴心"——它不随阶段切换而改变，而是持续运转的底层机制

---
