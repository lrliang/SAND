# D1：意图（Intent）阶段细化

好，两个阶段都值得独立成章。让我先深挖 Intent，再深挖 Learn——它们是 SDC 循环的"入口"和"出口"，定义了整个飞轮的品质。

---

## Intent 阶段深度拆解

### 为什么 Intent 是 SAND 最关键的输入阶段

[Framework DNA #27]：Intent 的质量决定了整个循环的上限
Concept：在传统开发中，"需求质量差"的后果是返工。在 AI 原生开发中，后果被放大了——AI 会忠实地、高效地、大规模地执行一个错误的意图。你越快发现意图定义有问题，浪费就越小。如果 Intent 定义错误在 Build 阶段才暴露，AI 已经生成了大量的"正确实现了错误目标"的代码
Novelty：AI 的高效率反而使"意图错误"的代价成倍增加——这是 SAND 把 Intent 单独成阶段（而非合并在 Build 中）的根本原因

---

### I1：意图声明标准（Intent Statement Standard）

[Framework DNA #28]：意图声明的 7 字段结构
Concept：SAND 定义的意图声明不是自然语言叙述，而是一个结构化的、人机双可读的标准格式。每个意图声明必须包含以下 7 个字段——

```yaml
intent_id: "SAND-2026-0042"
intent_type: feature | fix | refactor | exploration | optimization

# ── 第一组：人类决策域（Why + What）──

purpose: |
  为什么要做这件事？它解决什么业务问题或用户痛点？
  必须关联到一个可追溯的投资假设或业务目标。

desired_outcome: |
  成功之后，世界应该变成什么样子？
  用可观测的状态变化描述，而非实现细节。
  例："用户可以在3步内完成支付" 而非 "添加支付按钮"

# ── 第二组：契约域（How to verify）──

acceptance_criteria:
  - criterion: "支付流程在3步内完成"
    verification: "automated_e2e_test"
    priority: must
  - criterion: "支付失败时给出明确错误信息"
    verification: "human_review + automated_test"
    priority: must
  - criterion: "支付完成时间 < 2秒"
    verification: "performance_benchmark"
    priority: should

# ── 第三组：约束域（What NOT to do）──

constraints:
  technical:
    - "不得引入新的第三方支付SDK，使用现有集成"
    - "必须兼容现有订单数据结构"
  security:
    - "支付信息不得落地存储"
    - "所有支付接口必须使用HTTPS + 双向认证"
  scope:
    - "本次不包含退款流程"
    - "仅覆盖信用卡支付，其他方式后续迭代"

# ── 第四组：上下文域（Related knowledge）──

context_references:
  architecture: "docs/architecture/payment-module.md"
  domain_model: "docs/domain/order-payment-flow.md"
  prior_decisions: "ADR-0023: 选择Stripe作为支付网关"
  related_intents: ["SAND-2026-0038", "SAND-2026-0040"]
  known_risks: "上一轮Learn记录：Stripe webhook延迟问题"

# ── 第五组：元数据域 ──

meta:
  owner: "张三（问题域负责人）"
  priority: high
  investment_hypothesis: "IH-2026-007"
  estimated_ai_leverage: "适合Pipeline拓扑，预计AI杠杆率 5-8x"
  created: "2026-05-11"
  status: draft | reviewed | approved | in_execution | validated
```

Novelty：与 User Story（"As a... I want... So that..."）的三个本质区别——
1. 双受众设计：同时服务人类理解和 AI 执行，人读 purpose/desired_outcome，AI 解析 acceptance_criteria/constraints/context_references
2. 验证方式内嵌：每条验收标准自带验证方式（自动化测试/人工审查/性能基准），不需要另外写测试计划
3. 上下文自带：意图声明自带所有必需的上下文指针，AI 不需要"猜"或"问"

### [Framework DNA #29]：意图类型学（Intent Taxonomy）

Concept：不是所有意图都一样，SAND 定义 5 种意图类型，每种有不同的处理模式——

| 意图类型 | 描述 | 典型编排 | 审查强度 |
|------|------|------|------|
| Feature（功能） | 新增用户可感知的能力 | Pipeline 或 Hierarchy | HIP-2（同步审查） |
| Fix（修复） | 修正已知缺陷 | Solo | HIP-1 到 HIP-2 |
| Refactor（重构） | 改善内部结构不改变外部行为 | Solo 或 Pipeline | HIP-2（必须有回归测试） |
| Exploration（探索） | 技术可行性验证、方案探索 | Swarm | HIP-1（探索产物不直接上线） |
| Optimization（优化） | 性能、成本、体验优化 | Pipeline | HIP-2（需要基准对比数据） |

Novelty：意图类型直接关联到 Orchestrate 阶段的拓扑选择和 Validate 阶段的审查策略——意图类型是贯穿全循环的"路由标签"

### I2：执行契约标准（Execution Contract Standard）

[Framework DNA #30]：执行契约是意图与 AI 之间的"接口协议"
Concept：执行契约从意图声明中的 acceptance_criteria 进一步精化，变成 AI 可以形式化验证的通过/失败标准。它是人类意图和 AI 执行之间的"API 合约"——

```yaml
contract_id: "EC-SAND-2026-0042"
parent_intent: "SAND-2026-0042"

# 必须通过（Must Pass）：全部不满足则判定为失败
must_pass:
  - id: "MP-01"
    description: "支付流程步骤数 ≤ 3"
    test_type: e2e_automated
    test_path: "tests/e2e/payment-flow-steps.spec.ts"

  - id: "MP-02"
    description: "支付失败时展示用户友好的错误信息"
    test_type: hybrid  # AI初筛 + 人类终审
    ai_check: "错误消息不包含技术堆栈信息"
    human_check: "错误消息语言对非技术用户是否友好"

  - id: "MP-03"
    description: "所有支付API端点使用HTTPS + 双向认证"
    test_type: automated_security_scan
    scanner: "OWASP ZAP + 自定义TLS检查"

# 应当通过（Should Pass）：尽量满足，不满足需记录原因
should_pass:
  - id: "SP-01"
    description: "支付完成端到端时间 < 2秒（P95）"
    test_type: performance_benchmark
    baseline: "当前P95 = 3.2秒"

# 不得违反（Must Not Violate）：反向约束
must_not_violate:
  - id: "MNV-01"
    description: "不引入新的第三方SDK依赖"
    test_type: dependency_diff_check

  - id: "MNV-02"
    description: "不破坏现有订单API的向后兼容性"
    test_type: contract_test
    test_path: "tests/contract/order-api-compat.spec.ts"
```

Novelty：执行契约的三级结构（must_pass / should_pass / must_not_violate）直接映射到 Validate 阶段的三种判定结果——
- 全部 must_pass 通过 + 无 must_not_violate 违反 → 通过
- must_pass 通过但部分 should_pass 未满足 → 有条件通过（记录技术债）
- 任何 must_pass 失败或 must_not_violate 违反 → 打回 Build

### I3：意图分解模式（Intent Decomposition Patterns）

[Framework DNA #31]：大意图的分解策略
Concept：过大的意图会导致 AI 执行质量下降（上下文过载、验证困难）。SAND 提供三种标准的意图分解模式——

模式一：垂直切片（Vertical Slice）
大意图："实现完整支付系统"
│
├─ 意图A："实现信用卡支付的最小端到端流程"
├─ 意图B："添加支付失败的错误处理"
├─ 意图C："添加支付确认通知"
└─ 意图D："添加支付历史查询"
每个子意图都是用户可感知的完整价值切片，可独立验证。

模式二：能力分层（Capability Layering）
大意图："AI驱动的代码审查系统"
│
├─ 意图A："基础层——静态代码规范检查"
├─ 意图B："增强层——逻辑缺陷检测"
└─ 意图C："智能层——架构合规性评估"
每一层增加能力深度，前一层是后一层的基础。

模式三：风险梯度（Risk Gradient）
大意图："迁移到新的认证系统"
│
├─ 意图A："在测试环境验证新认证流程"（低风险）
├─ 意图B："灰度发布——5%流量切换"（中风险）
└─ 意图C："全量切换 + 旧系统退役"（高风险）
按风险递增排列，每一步都是对前一步的信心验证。

Novelty：传统的需求拆分关注"工作量均匀"，SAND 的意图分解关注"AI 可执行性"——每个子意图要小到一个 Agent 的单次上下文能完整覆盖，又大到能独立验证出有意义的价值

### I4：意图质量评审（Intent Quality Review）

[Framework DNA #32]：意图质量的 CLEAR 检查清单
Concept：每个意图声明在进入 Orchestrate 之前，必须通过 CLEAR 检查——

| 字母 | 维度 | 检查问题 |
|------|------|------|
| C | Complete（完整） | 7个必填字段是否全部填写？上下文引用是否有效（文件存在、链接可访问）？ |
| L | Lean（精简） | 是否存在超出范围的内容？scope 约束是否清晰划定了"不做什么"？ |
| E | Executable（可执行） | AI 拿到这个意图声明 + 引用的上下文后，是否能开始工作而无需再问人类？ |
| A | Assessable（可评估） | 每条验收标准是否有明确的验证方式？是否存在"看起来主观"的标准？ |
| R | Reversible（可回退） | 如果实现结果不理想，能否安全回退到执行前状态？回退策略是否定义？ |

Novelty：CLEAR 不是人类主观判断，其中 C/E/A 三项可以由 AI 自动化检查——这是"方法论即代码"的体现。AI 可以在意图声明提交时自动运行 CLEAR 检查并标记问题

### I5：意图生命周期（Intent Lifecycle）

[Framework DNA #33]：意图不是一次性工件，它有完整的生命周期
Concept：

```
Draft → Reviewed → Approved → In Execution → Validated → Archived
  │         │          │            │              │
  │         │          │            └─ 可回退到 Draft（意图偏差）
  │         │          └─ 可回退到 Reviewed（发现新约束）
  │         └─ 可回退到 Draft（审查未通过）
  └─ 可直接废弃（Abandoned）
```

每次状态变更都记录变更原因和操作人，形成完整的意图审计追踪链——这是治理中心轴在 Intent 阶段的具体体现。

Novelty：传统 User Story 一旦进入 Sprint 就几乎不变。SAND 的意图声明在整个循环中是"活的"——它可以被 Build 阶段的发现修正、被 Validate 阶段的结果挑战、被 Learn 阶段的经验丰富
