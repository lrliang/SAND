# D1：学习（Learn）阶段细化

Learn 阶段深度拆解

为什么 Learn 是 SAND 飞轮的动力源

[Framework DNA #34]：Learn 的核心使命不是"回顾"而是"资产化"
Concept：传统敏捷回顾（Retrospective）的产出是"行动项列表"——"下次我们应该…"。这些行动项大多依赖人类记忆和纪律来执行，衰减率极高。SAND 的 Learn 阶段产出的是可机器消费的
AI 资产——它们被注入下一轮循环的上下文中，由系统而非记忆来保障执行
Novelty：从"人记住教训"到"系统记住教训"——这是 AI 原生学习方式与传统回顾的本质区别

---
L1：AI 资产分类学（AI Asset Taxonomy）

[Framework DNA #35]：SAND 定义的 5 类可复用 AI 资产
Concept：Learn 阶段需要明确"什么值得资产化"。并非所有经验都值得沉淀，过度资产化反而污染上下文。SAND 定义 5 类 AI 资产——

| 资产类型 | 描述 | 来源阶段 | 消费阶段 | 示例 |
|---|---|---|---|---|
| 上下文资产（Context Asset） | 可复用的项目知识、架构决策、领域模型 | 全循环 | Orchestrate（O1上下文工程） | 架构决策记录（ADR）、领域模型文档、技术选型理由 |
| 意图模式（Intent Pattern） | 经过验证的高质量意图声明模板 | Intent + Validate | Intent（模板参考） | "支付类功能"意图模板、"性能优化类"意图模板 |
| 编排配方（Orchestration Recipe） | 经过验证的 Agent 拓扑 + 上下文策略组合 | Orchestrate + Build | Orchestrate（O2/O3） | "前端组件开发"编排配方、"API集成"编排配方 |
| 验证规则（Validation Rule） | 可复用的质量门禁规则、安全检查策略 | Validate | Validate（自动化检查） | 安全扫描规则集、性能基准阈值、合规检查清单 |
| 失败案例（Failure Case） | AI 失败的结构化记录——失败模式、根因、缓解措施 | 全循环 | Orchestrate（O5失败预案） | "Stripe webhook 延迟导致的幂等性问题"案例 |

Novelty：5类资产对应到 SDC 循环的不同消费点——这不是一个扁平的"知识库"，而是一个有结构的、按需注入的资产供应链

L2：资产化流程（Assetization Process）

[Framework DNA #36]：从原始数据到可复用资产的精炼流水线
Concept：不是所有循环中产生的信息都应该资产化。资产化是一个有门槛的提炼过程——

循环原始数据（Build日志、审查记录、Validate结果、运营数据）
│
▼
┌──────────────┐
│ L2a: 候选识别 │  AI自动扫描循环数据，标记资产化候选项
│              │  规则：重复出现≥2次的模式、重大失败、显著成功
└──────┬───────┘
│
▼
┌──────────────┐
│ L2b: 人类评审 │  变革催化师 + FDE+ 审查候选项
│              │  判断：是否有长期复用价值？是否特定于本次场景？
└──────┬───────┘
│
▼
┌──────────────┐
│ L2c: 结构化   │  将通过评审的候选项转化为标准资产格式
│              │  填充元数据：适用场景、失效条件、置信度
└──────┬───────┘
│
▼
┌──────────────┐
│ L2d: 注册入库 │  纳入组织资产库，设置版本号和过期审查周期
└──────────────┘

Novelty：关键的"人类评审"门禁防止了两种危险——(1) AI 错误地将偶然成功归结为可复用模式、(2) 将特定场景的解法过度泛化为通用资产

L3：资产质量与生命周期管理

[Framework DNA #37]：资产的衰减与刷新机制
Concept：AI 资产不是"一次写入永久有效"的。技术演进、模型更新、业务变化都可能使资产过时。SAND 为每类资产定义衰减策略——

| 资产类型 | 默认有效期 | 刷新触发条件 | 刷新方式 |
|---|---|---|---|
| 上下文资产 | 每季度审查 | 架构变更、技术栈升级 | 人工审查 + AI辅助差异检测 |
| 意图模式 | 每半年审查 | 验证通过率下降、新模型能力变化 | 基于最近使用数据重新评估 |
| 编排配方 | 每季度审查 | AI 工具/模型更新、新拓扑模式出现 | 在新环境下重新验证有效性 |
| 验证规则 | 持续有效（无过期） | 合规标准变更、安全漏洞库更新 | 由合规/安全团队维护 |
| 失败案例 | 永久保留 | 根因已被彻底消除 | 标记为"已解决"但保留供参考 |

Novelty：资产有"置信度衰减"——每次被使用且验证通过，置信度+1；每次使用但发现不适用，置信度-1；长期未使用，置信度缓慢衰减。低置信度资产在下次审查时被优先评估

[Framework DNA #38]：资产的版本化与可追溯性
Concept：每个 AI 资产必须版本化管理，记录——
  - 创建来源：哪个循环、哪个意图产生了这个资产
  - 变更历史：谁在什么时候为什么修改了它
  - 使用记录：被哪些后续意图引用过、效果如何
  - 关联关系：与其他资产的依赖/互补/冲突关系

这实现了 SAND 声明中"可治理可审计原则"在 Learn 阶段的落地

L4：AI 复盘会议（Blame-free AI Retrospective）

[Framework DNA #39]：AI 复盘的标准议程
Concept：Learn 阶段的核心仪式是"AI复盘会议"，但它与传统 Retrospective 有根本区别——

传统 Retro 问：
  - 什么做得好？什么做得不好？下次怎么改进？

SAND AI 复盘问：

| 议题 | 聚焦点 | 产出 |
|---|---|---|
| 意图质量回顾 | 本轮意图声明的 CLEAR 评分分布如何？哪些意图经历了回退？回退原因是什么？ | 意图模式改进建议 |
| 编排效果回顾 | Agent 拓扑选择是否合理？上下文策略是否充分？哪些人类介入点被证明是多余的或不足的？ | 编排配方更新 |
| AI 杠杆率分析 | 本轮 AI 杠杆率是多少？瓶颈在哪里——是 AI 能力不足，还是上下文不完整，还是人类审查太慢？ | 效率优化方向 |
| 失败模式复盘 | 本轮出现了哪些 AI 失败？是否有新的失败模式需要加入分类学？现有缓解策略是否有效？ | 失败案例资产、缓解策略更新 |
| 资产化提名 | 本轮有哪些经验值得资产化？由谁提名？初步归入哪类资产？ | 资产化候选清单 |

Novelty：核心理念——复盘的对象不是人的表现，而是人-AI协作系统的表现。不问"谁犯了错"，问"系统设计的哪个环节导致了这个结果"

L5：飞轮加速度量（Flywheel Acceleration Metrics）

[Framework DNA #40]：如何量化飞轮是否在加速
Concept：Learn 阶段需要回答一个终极问题——"我们是否在变得更好？" SAND 定义三个飞轮加速指标——

  1. 资产复用率（Asset Reuse Rate）
  - 定义：本轮循环中引用了已有资产的意图占比
  - 健康范围：30%-70%（太低说明资产未被使用，太高说明创新不足）
  - 趋势意义：逐轮上升 → 飞轮在加速

  2. 意图首通率（Intent First-Pass Rate）
  - 定义：意图声明从 Approved 到 Validated 中间无需回退的比例
  - 健康范围：>60%（成熟团队可达80%+）
  - 趋势意义：逐轮上升 → 意图定义能力在提升

  3. 循环周期压缩率（Cycle Time Compression）
  - 定义：同类型意图从 Intent 到 Validate 的平均耗时，与历史均值的比值
  - 健康范围：<1.0 说明在加速
  - 趋势意义：持续<1.0 → 整个系统在变得更高效

Novelty：这三个指标形成一个三角——资产复用率衡量"系统记忆"，首通率衡量"意图质量"，周期压缩率衡量"端到端效率"。三者同时改善才是真正的飞轮加速
