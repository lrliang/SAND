# D1：运营（Operate）阶段细化

## Operate 在 AI 原生语境下的重定义

### [Framework DNA #55]：Operate 不只是"运维"，是"AI持续价值兑现"

Concept：传统运维的核心是"保持系统稳定运行"。SAND 的 Operate 阶段有更丰富的使命——

1. 稳定运行（传统职责）：部署、监控、告警、事故响应
2. 持续验证（AI 原生新增）：在生产环境中持续验证 Intent 是否真正实现了业务目标
3. 信号采集（AI 原生新增）：采集运营数据作为下一轮 Learn 的输入
4. 自适应优化（AI 原生新增）：AI 基于运营数据主动提出优化建议

---

## Op1：AI 辅助运营模型（AI-Assisted Operations Model）

### [Framework DNA #56]：三级运营自动化

Concept：类似人类介入模型（HIP），Operate 阶段也有三级自动化——

| 级别 | 名称 | AI 行为 | 人类行为 | 适用场景 |
|------|------|---------|----------|----------|
| OPS-1 | AI 自主处理 | 检测异常 → 自动执行预定义修复 → 记录日志 | 事后审阅日志 | 已知问题的标准修复（自动扩缩容、缓存清理、服务重启） |
| OPS-2 | AI 建议+人工执行 | 检测异常 → 分析根因 → 生成修复方案 → 等待人类批准 | 审查方案 → 批准/修改 → 监督执行 | 中等风险操作（数据库迁移、配置变更、依赖更新） |
| OPS-3 | AI 信息+人工决策 | 提供异常数据、历史对比、影响分析 | 独立判断和决策 | 高风险事件（安全事件、数据泄露、重大服务中断） |

Novelty：OPS-1 级别的自动化需要经过严格的"信任积累"——新加入的自动修复规则从 OPS-2 开始，人类批准 N 次无问题后才升级为 OPS-1。这与 HIP 的动态调整机制同源

## Op2：生产环境意图验证（Production Intent Validation）

### [Framework DNA #57]：从"系统健康"到"意图实现"的运营视角跃迁

Concept：传统监控关注"系统是否健康"（CPU、内存、延迟、错误率）。SAND 的 Operate 加入一层更高阶的监控——意图是否在生产环境中真正实现了？

```yaml
intent_production_validation:
  intent_ref: "SAND-2026-0042"
  desired_outcome: "用户可以在3步内完成支付"

  production_metrics:
    - metric: "实际支付步骤数中位数"
      target: "≤ 3"
      actual: "2.7"
      status: "达标"

    - metric: "支付完成率"
      target: "提升（相对于上线前基线）"
      baseline: "72%"
      actual: "81%"
      status: "达标，+9%"

    - metric: "支付相关客诉数"
      target: "下降"
      baseline: "每周23件"
      actual: "每周11件"
      status: "达标，-52%"

  validation_conclusion: "意图在生产环境中验证通过"
  investment_hypothesis_status: "IH-2026-007 证实——支付简化带来转化率提升"
```

Novelty：这把 Validate 阶段的"技术验证"延伸为 Operate 阶段的"业务验证"——不仅测试通过了，而且真正解决了业务问题。这是对 v2 中"投资假设验证速率"指标的操作化实现

## Op3：运营信号采集（Operational Signal Collection）

### [Framework DNA #58]：Operate 是 Learn 的数据来源

Concept：Operate 阶段系统性地采集四类信号，为 Learn 阶段提供原材料——

| 信号类型 | 采集内容 | 采集方式 | Learn 阶段用途 |
|----------|----------|----------|----------------|
| 业务信号 | 用户行为数据、转化率、满意度 | 埋点+分析平台 | 验证投资假设、校准未来意图优先级 |
| 技术信号 | 性能数据、错误日志、资源消耗 | APM+日志平台 | 识别技术债、优化编排配方 |
| AI 行为信号 | AI 在运营中的决策记录、自动化执行日志 | Agent 日志 | 评估 AI 可信度、调整自动化级别 |
| 异常信号 | 事故报告、异常检测结果、根因分析 | 告警系统+AI分析 | 失败案例资产化、缓解策略更新 |

Novelty：传统运营数据用于"排障"，SAND 的运营数据用于"学习和改进整个 SDC 循环"——数据不是终结在运维团队手中，而是流回到下一轮 Assess

## Op4：AI 辅助事故响应（AI-Assisted Incident Response）

### [Framework DNA #59]：事故响应的 AI 原生流程

Concept：当生产环境出现重大异常时——

```
异常检测（AI 自动）
    │
    ├─ 已知模式 → 匹配失败案例库 → 推荐已验证的修复方案（OPS-1/2）
    │
    └─ 未知模式 → AI 实时分析
         │
         ├─ 影响范围评估（多少用户/多少业务受影响）
         ├─ 根因假设生成（基于日志、代码变更历史、架构拓扑）
         ├─ 修复方案草拟（可能多方案并行，Swarm 模式）
         │
         └─→ 人类决策者审查 → 选择方案 → 执行 → 事后纳入失败案例库
```

Novelty：事故响应的"已知/未知"分流是 Orchestrate 阶段 Agent 拓扑模式在运营中的应用——已知问题用 Solo/Pipeline，未知问题用 Swarm

## 阶段间关系的全景总结

### [Framework DNA #60]：SDC 七阶段的流转节奏

Concept：把所有阶段放在一起，SDC 的完整运转模式如下——

```
           ┌──────────────────────────────────────┐
           │          Governance（治理中心轴）        │
           │   决策治理 · 合规治理 · 质量治理 · 审计治理   │
           └──────────────────────────────────────┘
                            │
    ┌───────────────────────┼───────────────────────┐
    │                       │                       │
    ▼                       ▼                       ▼

 Assess ──→ Intent ──→ Orchestrate ──→ Build ──→ Validate ──→ Operate ──→ Learn
   ▲                                     ↑          │                       │
   │                                     │          │ 打回                  │
   │                                     └──────────┘ Build                 │
   │                         ↑                      │                       │
   │                         │                      │ 重定向                 │
   │                         └──────────────────────┘ Intent                │
   │                                                                        │
   └────────────────────────── 飞轮闭环 ────────────────────────────────────┘
                        资产反馈 + 校准信号
```

**非均匀节奏：**
- Assess：首次2-4周 / 循环校准1-2天
- Intent：数小时到数天（取决于意图复杂度）
- Orchestrate：数小时（成熟团队可复用编排配方，分钟级）
- Build：脉冲式，每个脉冲 AI 生成10-30分钟 + 人类审查30-60分钟
- Validate：三通道并行，数小时到1天
- Operate：持续运行
- Learn：每轮循环结束，1-2天集中
