# D1：编排（Orchestrate）阶段细化

好，让我们把 Orchestrate 阶段拆到原子级别。这是 SAND 对整个行业最大的原创贡献——其他框架都没有这个概念。

---

[Framework DNA #16]：Orchestrate 是 SAND 的"发动机室"
Concept：如果 SDC 是一辆车，Intent 是方向盘，Build 是车轮，那 Orchestrate 就是发动机。它决定了"同样的意图，能以多高的效率和质量被实现"。一个优秀的编排方案可以让一个 FDE+ 以 10x 杠杆率工作，一个糟糕的编排方案会让 AI 成为拖累
Novelty：这是软件工程中第一次需要一个专门的阶段来设计"人和 AI 怎么协作"——以前从不需要，因为工具是确定性的、被动的

让我把 Orchestrate 拆解为 5个子过程：

---

## Orchestrate 的 5 个子过程

### O1：上下文工程（Context Engineering）

> "AI 的能力上限 = 模型能力 × 上下文质量"

[Framework DNA #17]：上下文工程是 AI 原生开发的第一核心能力
Concept：上下文工程不是"写 Prompt"，而是系统性地设计 AI 在执行任务时需要获取的全部信息架构。它回答一个核心问题——"AI 需要知道什么才能正确理解并执行这个意图？"

上下文工程包含四个层次：

| 层次 | 内容 | 示例 |
|------|------|------|
| 项目上下文 | 架构决策、技术栈、编码规范、领域模型 | CLAUDE.md、架构文档、API Schema |
| 意图上下文 | 当前意图声明、执行契约、约束边界 | 本次任务的结构化需求 |
| 历史上下文 | 相关的过往决策、已知陷阱、复盘教训 | 上一轮 Learn 沉淀的模式库 |
| 协作上下文 | 其他 Agent 的产出、团队成员的反馈、依赖关系 | 上游 Agent 的输出，待集成的接口定义 |

Novelty：传统开发中，上下文是隐含在人脑中的（"你得找老王问一下这个接口为什么这么设计"）。AI 原生开发中，上下文必须外化、结构化、可机器读取——否则 AI 就是在盲人摸象

[Framework DNA #18]：上下文质量评估模型（Context Quality Model）
Concept：SAND 需要定义上下文质量的可度量标准——
- 完整性（Completeness）：AI 执行此意图所需的信息是否全部包含？
- 准确性（Accuracy）：提供的上下文是否与当前代码/架构状态一致（而非过时的文档）？
- 精简性（Conciseness）：是否剔除了无关噪音？（过多的上下文同样有害——稀释关键信息、浪费 token）
- 可发现性（Discoverability）：AI 能否自主找到它需要的上下文，还是需要人类手动喂入？

Novelty：这是 SAND 独创的质量维度。没有任何现有框架讨论"上下文质量"，因为在 AI 之前这个概念不存在

[Framework DNA #19]：上下文资产的组织形态
Concept：上下文不应该是散落的文件，而应该是一个有结构的资产库。借鉴 bmad-method 的模式——
- 项目级上下文：CLAUDE.md / project-context.md → 始终加载
- 领域级上下文：按业务域组织的知识库 → 按需加载
- 意图级上下文：每个意图声明自带的局部上下文 → 随意图流转
- 临时上下文：当前会话中积累的对话/决策 → 会话结束后提炼为资产或丢弃

这形成一个上下文金字塔：塔底是稳定的组织知识，塔尖是易变的当前任务信息

### O2：Agent 选型与配置（Agent Selection & Configuration）

> "用正确的 AI 做正确的事"

[Framework DNA #20]：Agent 选型决策框架
Concept：不是所有任务都需要最强的模型，也不是所有任务都适合 Agent。Orchestrate 需要一个决策框架来选择正确的 AI 参与方式——

任务特征评估
│
├─ 确定性高 + 规则清晰 → 传统自动化/脚本（不用 AI）
│
├─ 确定性中 + 模式可识别 → 轻量模型 + 严格约束
│    例：代码格式化、简单测试生成、文档模板填充
│
├─ 确定性低 + 需要理解力 → 重量级模型 + 人类审查
│    例：架构设计建议、复杂代码重构、需求澄清
│
└─ 高度创造性 + 开放式 → 多模型探索 + 人类仲裁
例：解决方案探索、技术选型分析、创新方案设计

Novelty：这是"不浪费的 AI 使用"原则的操作化实现——SAND 声明中写了"不为了用AI而用AI"，Agent 选型框架就是这条原则的落地工具

[Framework DNA #21]：Agent 能力卡（Agent Capability Card）
Concept：每个可用的 AI Agent/工具应该有一张标准化的"能力卡"，供 AI 编排师在 Orchestrate 阶段参考——

agent_id: code-reviewer-v1
capability_domain: 代码审查
model_requirement: Sonnet 级别以上
context_window_need: 中（~50K tokens）
input_format: Git diff + 架构规范
output_format: 结构化审查报告（问题清单+严重级别+修复建议）
human_oversight: 必需——AI 标记问题，人类做最终决策
known_limitations:
  - 跨文件架构级问题检出率较低
  - 对业务逻辑正确性的判断不可靠
cost_profile: 低（单次调用 ~$0.05）
reliability: 高（幻觉率 <5%）

Novelty：类似 bmad-method 中 Agent 有 name/title/personality/expertise 的定义，但 SAND 的 Agent 能力卡面向的是选型决策，不是执行人格

### O3：拓扑设计（Topology Design）

> "Agent 之间、Agent 与人之间如何连接？"

[Framework DNA #22]：四种标准拓扑模式的深化定义

模式一：Solo（独奏）
[FDE+] ←→ [单 Agent]
- 适用场景：明确的小范围任务，单一技能域
- 决策流：FDE+ 给意图 → Agent 产出 → FDE+ 审查 → 完成/重试
- 优势：简单、快速、上下文开销最小
- 风险：Agent 能力不足时无冗余

模式二：Pipeline（流水线）
[FDE+] → [Agent-A] → [Agent-B] → [Agent-C] → [FDE+ 终审]
- 适用场景：标准化多步骤交付（需求→设计→代码→测试）
- 决策流：每个 Agent 的输出是下一个的输入，FDE+ 在关键衔接点设检查门
- 优势：可预测、可复现、适合成熟的重复性流程
- 风险：前序 Agent 错误会向后传播（"垃圾进垃圾出"链式放大）
- 缓解：每个衔接点设置自动化验证 + 人类抽检

模式三：Swarm（蜂群）
┌→ [Agent-A] ─┐
[FDE+] ──┼→ [Agent-B] ──┼→ [FDE+ 仲裁/综合]
└→ [Agent-C] ─┘
- 适用场景：探索性问题、需要多角度方案对比
- 决策流：多个 Agent 并行探索同一意图的不同实现路径，FDE+ 比较、选择或综合
- 优势：降低单一 AI 路径依赖，利用 AI 的非确定性产生多样性
- 风险：成本较高（多次调用），需要 FDE+ 有强裁决能力
- 关键创新：这是唯一一种"把 AI 的非确定性从 bug 变成 feature"的拓扑——Fowler 说的"幻觉即特征"在这里得到最好的实践

模式四：Hierarchy（层级）
[FDE+ 指挥官]
│
[Orchestrator Agent]
┌────────┼────────┐
[Agent-A] [Agent-B] [Agent-C]
- 适用场景：大型系统构建、多模块并行开发
- 决策流：FDE+ 设定高阶目标，Orchestrator Agent 分解任务并分派给子 Agent，子 Agent 独立执行并汇报
- 优势：可扩展、适合复杂项目
- 风险：Orchestrator Agent 本身可能引入错误的任务分解
- 缓解：FDE+ 审查 Orchestrator 的分解方案，而不是审查每个子 Agent 的细节

[Framework DNA #23]：拓扑选择决策矩阵
Concept：AI 编排师用这个矩阵来快速决策——

|  | 低不确定性 | 高不确定性 |
|------|------|------|
| 小规模 | Solo | Swarm |
| 大规模 | Pipeline | Hierarchy + Swarm 混合 |

Novelty：这是第一次有人把"人-AI协作架构"当作"需要设计的架构决策"来对待，并提供了选型工具

### O4：人类介入点设计（Human Intervention Point Design）

> "人在哪里介入？以什么方式？介入多深？"

[Framework DNA #24]：三级人类介入模型
Concept：不是每个 AI 输出都需要同等强度的人类审查。SAND 定义三个级别——

| 级别 | 名称 | 触发条件 | 人类行为 | 示例 |
|------|------|------|------|------|
| HIP-1 | 异步知晓（Async Awareness） | AI 自信度高、任务风险低 | 人类事后批量浏览 AI 日志，抽样检查 | 格式化、简单重构、文档更新 |
| HIP-2 | 同步审查（Sync Review） | AI 自信度中等或任务有中等风险 | 人类在 AI 产出后立即审查，做"接受/修改"决策 | 功能代码生成、测试设计、API 变更 |
| HIP-3 | 人类主导（Human-Led） | 任务涉及架构决策/安全/合规/商业判断 | 人类做主要决策，AI 仅提供信息和建议 | 架构设计、安全策略、上线决策、投资决策 |

Novelty：传统开发中，审查强度取决于代码复杂度。SAND 中，审查强度取决于AI 输出的风险等级和 AI 的可信度——这是全新的审查维度

[Framework DNA #25]：介入点的动态调整机制
Concept：介入级别不是静态的，它应该随以下信号动态调整——
- AI 信任度积累：某类任务 AI 连续 N 次通过人类审查无修改 → 该类任务的介入级别可降一级
- 异常信号：AI 产出出现新类型的错误 → 该类任务的介入级别升一级
- 领域变化：进入新的业务域或技术域 → 全面回到 HIP-2 以上

这创造了一个自适应的信任校准机制——既不过度审查（浪费人力），也不过度信任（引入风险）

---

### O5：失败模式规划（Failure Mode Planning）

> "AI 出错了怎么办？"

[Framework DNA #26]：AI 失败模式分类学
Concept：SAND 需要一个标准化的 AI 失败模式分类，供 Orchestrate 阶段做预案——

| 失败模式 | 描述 | 检测方式 | 缓解策略 |
|------|------|------|------|
| 幻觉生成 | AI 生成事实错误的内容（不存在的 API、错误的业务逻辑） | 执行契约验证、自动化测试 | Swarm 拓扑交叉验证、强制引用检查 |
| 上下文遗失 | AI 在长对话中丢失早期上下文 | 关键信息回归测试 | 上下文压缩策略、分段执行、关键信息锚定 |
| 偏见放大 | AI 基于训练数据中的偏见产出不当内容 | 多样性检查、边界用例测试 | 多模型交叉验证、人类多样性审查 |
| 能力越界 | AI 尝试处理超出其能力范围的任务 | 置信度监控、输出质量断崖检测 | Agent 能力卡边界标注、自动路由到人类 |
| 级联失败 | Pipeline 中前序错误被后续 Agent 放大 | 衔接点自动化验证 | 每个衔接点设质量门禁、异常时中断流水线 |

Novelty：这是"Fowler的容差思维"的操作化——不是抽象地说"要容忍AI的非确定性"，而是具体地分类每种失败、定义检测和缓解手段

## Orchestrate 阶段的整体工作流

把5个子过程组合起来，Orchestrate 阶段的标准执行流如下：

```
Intent 阶段产出
       │
       ▼
  ┌─────────────┐
  │ O1: 上下文工程 │ → 上下文策略文档
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │ O2: Agent选型 │ → Agent 组合方案
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │ O3: 拓扑设计  │ → Agent 拓扑图
  └──────┬──────┘
         │
         ▼
  ┌──────────────┐
  │ O4: 介入点设计 │ → 人类介入点定义
  └──────┬───────┘
         │
         ▼
  ┌──────────────┐
  │ O5: 失败模式  │ → 风险缓解预案
  └──────┬───────┘
         │
         ▼
  《编排方案》完成 → 进入 Build
```
