# 决策治理

关键决策点的人类最终确认权（Human-in-the-Loop）。架构设计、安全审查、上线批准必须有人类参与和最终确认。

---

## 概述

决策治理是 SAND 治理中心轴四根支柱中承担"决策权力分配"角色的支柱。它定义在 AI 辅助开发过程中，哪些决策必须由人类做出最终判断——不是因为 AI 不能做，而是因为这些决策的后果需要有人类承担责任。

**理论基础：**

1. **HIP 三级人类介入模型**（参见 [人类介入模型](../orchestrate/human-intervention.md)）：HIP-1/2/3 定义了 AI 自主度的三个级别，本文档定义的是治理层面何时触发哪个级别
2. **McKinsey (2025) "State of AI"**：65% 的 AI 高绩效组织已定义 Human-in-the-Loop 流程——决策治理的缺失是 AI 治理差距的首要指标
3. **Hassan SE 3.0 自主级别**（参见 [认知协作理论](../../01-foundations/cognitive-collaboration.md)）：SASE 框架定义的 Level 1-5 自主级别为决策权限分配提供了渐进式框架

**核心原则：**

- **人类最终确认权不可让渡**：关键决策点的人类确认权是组织治理的基本要求，不随 AI 能力提升而改变
- **决策记录是审计基础**：每个人工确认都记录为 `human_confirmations` 事件，构成审计证据链的关键节点
- **HIP 方向不可反转**：HIP-1 = 最低介入，HIP-3 = 最高介入——此方向已在 PRD FR17 和 Architecture 中统一确认

## 关键决策点分类

### 五类关键决策

| 决策类别 | 定义 | 典型场景 | 默认 HIP |
|---------|------|---------|---------|
| **架构决策** | 影响系统结构和长期演进的技术选择 | 新增组件、重大重构、技术栈变更、API 契约变更 | HIP-2 |
| **安全决策** | 涉及系统安全性和数据保护的选择 | 认证/授权逻辑变更、加密方案选择、安全策略配置 | HIP-3 |
| **数据决策** | 影响数据模型和数据流的选择 | Schema 迁移、数据分类变更、存储策略调整 | HIP-2 |
| **业务逻辑决策** | 影响业务规则和用户行为的选择 | 核心业务流程变更、计费逻辑、权限规则 | HIP-2 |
| **合规决策** | 涉及法规遵从和政策执行的选择 | 合规标准映射、审计策略调整、数据隐私配置 | HIP-3 |

## 人类确认权矩阵

### 决策类型 × HIP 级别 × 确认要求

| 决策类别 | HIP-1（全自主） | HIP-2（关键审查） | HIP-3（全程监督） |
|---------|----------------|-------------------|-------------------|
| **架构决策** | 事后审查日志 | **确认拓扑选型和组件边界** | 全程参与设计讨论 |
| **安全决策** | ⚠️ 不推荐 | **确认安全方案 + 审查实现** | 全程监督 + 安全专审 |
| **数据决策** | 事后审查迁移结果 | **确认 Schema 变更方案** | 全程参与设计 + 回滚预案审批 |
| **业务逻辑** | 事后验收 | **确认业务规则 + 边界条件** | 全程参与逻辑设计 |
| **合规决策** | ⚠️ 不推荐 | **确认合规方案** | 全程参与 + 法务/合规团队审批 |

**⚠️ 标记说明：** 安全决策和合规决策在 HIP-1 下不推荐执行。如果组织配置允许，审计报告中将高亮标记为潜在合规风险。

## 决策记录标准

### 与 SandAuditEvent 的 human_confirmations 对齐

每条人工确认记录遵循 `schemas/audit-event.schema.json` 中 `human_confirmations` 数组的结构：

```json
{
  "step": "step-02-draft",
  "timestamp": "2026-05-12T10:15:00Z",
  "decision": "approved"
}
```

**字段定义：**

| 字段 | 类型 | 允许值 | 含义 |
|------|------|--------|------|
| `step` | string | step-{NN}-{name} | 确认发生的步骤标识 |
| `timestamp` | string | ISO-8601 UTC | 确认时间（UTC） |
| `decision` | string | approved / rejected / deferred | 人类决策结果 |

**三种决策结果的语义：**

| 决策 | 含义 | 后续行为 |
|------|------|---------|
| `approved` | 确认通过，继续执行 | Skill 继续下一步 |
| `rejected` | 否决，需要修改 | 打回到前一步或 Build 阶段 |
| `deferred` | 暂缓决策，需要更多信息 | Skill 暂停，等待人类补充信息后恢复 |

**记录完整性要求：** HIP-2 和 HIP-3 下，每个标记为需要人工确认的步骤必须有对应的 `human_confirmations` 记录。`sand-governance-audit` 的审计报告中将检测并高亮缺失确认的事件。

## 决策升级机制

### 自动升级触发条件

| 触发条件 | 升级行为 | 理论依据 |
|---------|---------|---------|
| AI 不确定性高于阈值 | 升级到 HIP-2 或 HIP-3 | AI 输出置信度低时，应交由人类判断 |
| 跨领域决策 | 强制 HIP-2 以上 | 新领域缺乏历史执行数据，信任度回归基线 |
| 质量门禁未通过 | 按质量治理升级规则 | 参见 [质量治理](./quality-governance.md) HIP 交互节 |
| 异常信号检测 | 按 HIP 动态调整机制 | 参见 [人类介入模型](../orchestrate/human-intervention.md) 动态调整 |
| 连续失败超过阈值 | 升级到 HIP-3 | 连续失败表明任务超出当前 AI 能力边界 |

### 降级条件（仅通过信任度积累）

决策权限只能通过以下条件降级（从高 HIP 到低 HIP）：

1. **人类显式确认降级**：降级需人类主动批准，不可自动降级
2. **信任度积累**：在同一领域连续成功执行 N 次后，可建议降级（N 值由 `.sand/config.yaml` 配置）
3. **新领域重置**：进入新的 capability_domain 时，HIP 回归 HIP-2 以上

## 决策治理在 SDC 各阶段的体现

| SDC 阶段 | 关键决策点 | 决策类别 | 默认 HIP |
|---------|-----------|---------|---------|
| **Assess** | 评估结论确认——7 维度评级和改进路径选择 | 业务逻辑 | HIP-2 |
| **Intent** | 意图审查——意图声明 7 字段完整性和 CLEAR 通过确认 | 业务逻辑 | HIP-2 |
| **Orchestrate** | 拓扑选型确认——编排方案和 HIP 级别配置 | 架构决策 | HIP-2 |
| **Build** | 关键代码审查——安全关键路径和核心业务逻辑 | 安全/业务 | HIP-2/3 |
| **Validate** | 验证决策——通过/有条件通过/打回/重定向 | 质量决策 | HIP-2 |
| **Operate** | 度量异常响应——度量指标超出基线时的处理决策 | 业务逻辑 | HIP-2 |
| **Learn** | 资产入库审批——复盘产出的资产分类和入库确认 | 业务逻辑 | HIP-1 |

**Governance（治理中心轴）本身不是 SDC 阶段**，而是贯穿所有 7 个阶段的持续机制。上表中的决策点覆盖了治理中心轴在各阶段的具体体现。

**对 SAND 的实践意义：** 决策治理通过 HIP 机制与每个 SDC 阶段耦合。每个阶段的 Skill 在执行到需要人类决策的步骤时，根据 HIP 配置决定是自动继续（HIP-1）、请求确认（HIP-2）还是全程等待人类指导（HIP-3）。所有确认记录自动流入审计证据链。
