# 质量治理

AI产出的审查覆盖率、质量门禁标准。三层审查策略的执行监督。

---

## 概述

质量治理是 SAND 治理中心轴四根支柱中承担"质量保障"角色的支柱。它解决的核心问题：**如何确保 AI 生成的交付物在合并到生产代码前有系统性的质量保障？**

**理论基础：**

1. **Fowler 非确定性范式**（参见 [非确定性编程范式](../../01-foundations/non-deterministic-paradigm.md)）：AI 输出的概率性本质要求约束工程的双控制分类——计算控制（确定性检查）和推断控制（语义分析）
2. **Mikkonen Cargo Cult 理论**（参见 [生成式复用风险](../../01-foundations/generative-reuse-risk.md)）：单一代码审查在 AI 生成场景中存在系统性不足——Cargo Cult 盲区、维度覆盖不足、非确定性累积
3. **三通道并行验证**（参见 [三通道架构](../validate/three-channel.md)）：契约验证 + 安全合规 + 架构对齐的并行检查是质量治理的技术实现

**核心原则：** 质量治理不是"审查更多"，而是"在正确的层级用正确的方式审查"——自动化处理确定性检查，AI 辅助处理模式识别，人工聚焦于需要深度判断的决策。

## AI 产出审查覆盖率标准

### 按代码类型分级

不同类型的代码需要不同级别的审查覆盖：

| 代码类型 | 审查要求 | 理由 | HIP 对应 |
|---------|---------|------|---------|
| **核心业务逻辑** | 100% 人工审查 | 业务正确性无法完全自动化验证 | HIP-3 |
| **安全关键路径** | 100% 人工审查 + 安全专审 | 认证/授权/加密的错误后果不可逆 | HIP-3 |
| **一般功能代码** | AI 三通道验证 + 抽样人工审查 | 平衡效率与质量 | HIP-2 |
| **辅助代码** | AI 三通道验证 | 工具函数、适配器等低风险代码 | HIP-1 |
| **测试代码** | AI 自审核 + 覆盖率检查 | 测试代码有自验证性 | HIP-1 |
| **配置/文档** | 格式校验 + Schema 验证 | 确定性检查即可 | HIP-1 |

**对 SAND 的实践意义：** 审查覆盖率标准驱动 `sand-validate-delivery` 的验证深度。核心业务逻辑和安全路径触发 L3 人工深度审查，辅助代码仅触发 L1-L2 自动化/AI 辅助审查。

## 三层审查策略

### L1：自动化审查（计算控制层）

**目标：** 用确定性工具消除确定性缺陷。

| 检查类型 | 工具/方法 | 判定标准 |
|---------|---------|---------|
| 语法检查 | lint 工具（ESLint/Pylint 等） | 零 error，warn 可接受 |
| 类型检查 | TypeScript/mypy 等 | 零类型错误 |
| 测试通过 | 项目测试框架 | 100% 通过，无回归 |
| Schema 校验 | JSON Schema 验证 | 必填字段完整 |
| 格式规范 | prettier/black 等 | 零格式偏差 |

**触发时机：** 每次 Build 阶段产出交付物时自动运行。
**SAND 对应：** `sand-validate-delivery` 的 step-01-contract-check 中的确定性检查部分。

### L2：AI 辅助审查（推断控制层）

**目标：** 用 AI 的模式识别能力检测人类可能遗漏的语义问题。

这一层对应 `sand-validate-delivery` 的三通道并行验证：

| 通道 | 检查内容 | 理论基础 |
|------|---------|---------|
| **契约验证** | 交付物是否满足执行契约的 must_pass/should_pass/must_not_violate | 意图驱动开发的闭环验证 |
| **安全合规** | 注入、XSS、敏感数据泄露、许可证合规 | Cargo Cult 盲区——开发者信任但不理解 |
| **架构对齐** | 命名规范、目录结构、依赖关系、分层约束 | 非确定性累积——小偏差积累成架构腐化 |

**触发时机：** 交付物提交验证时（`sand-validate-delivery` 激活时）。

### L3：人工深度审查（专家判断层）

**目标：** 对需要领域知识和深度判断的决策进行人类审查。

| 审查场景 | 审查要求 | 专审角色 |
|---------|---------|---------|
| 架构设计决策 | 新增组件/重大重构需架构师审查 | 架构师 |
| 安全关键路径 | 认证/授权/加密变更需安全审查 | 安全工程师 |
| 数据模型变更 | Schema 迁移需 DBA 审查 | DBA |
| 外部 API 契约 | 公开 API 变更需 API 设计审查 | API 负责人 |
| 业务规则变更 | 核心业务逻辑需产品确认 | 产品经理 |

**触发时机：** HIP-2/3 配置下的关键决策点（参见 [决策治理](./decision-governance.md)）。

**与 PRD Journey 1 林涛路径 A 的对齐：** 林涛的三层审查策略（L1 自动化 → L2 AI 辅助 → L3 深度人工仅用于架构决策）直接映射到本节定义的三层模型，预期效果为 PR 审查中位时间 -40%。

## 质量门禁设计原则

### SDC 各阶段质量关卡

| SDC 阶段 | 质量关卡 | 通过标准 | 失败处理 |
|---------|---------|---------|---------|
| **Intent** | CLEAR 检查 | 5 维全部 ✓ 或 ⚠️（可接受） | 打回修正意图声明 |
| **Orchestrate** | 拓扑可行性 | 推荐拓扑与意图复杂度匹配 | 建议调整拓扑或分解意图 |
| **Build** | 构建完成性 | 代码可编译/可运行，L1 检查通过 | 打回 Build 阶段修复 |
| **Validate** | 三通道验证 | 决策矩阵判定≥"有条件通过" | 打回 Build 或重定向 Intent |
| **Learn** | 资产质量评估 | 复盘日志结构完整，资产分类合理 | 补充复盘内容 |

### 质量门禁触发阈值

MVP 定义质量门禁框架，不强制量化阈值——各组织根据实际情况在 `customize.toml` 中配置：

```toml
[quality_gates]
# Intent 阶段
clear_check_min_pass = 3      # CLEAR 最少通过维度数（5 维中）

# Validate 阶段
contract_check_must_pass = true # must_pass 全部通过才算通过
security_blocking_threshold = 0 # 安全 blocking 级发现数上限

# 覆盖率
min_test_coverage = 0          # 最低测试覆盖率（0=不强制）
```

## 质量度量基线

### 与轻量度量的关系

质量治理依赖 `sand-measure-light`（Story 7-0/7-1）提供的度量信号作为输入：

| 度量信号 | 质量治理用途 |
|---------|------------|
| **PR 周期时间** | 衡量三层审查策略的效率影响 |
| **变更失败率** | 衡量质量门禁的拦截效果 |
| **AI 参与度** | 评估审查覆盖率标准的适用范围 |
| **部署频率** | 衡量质量门禁是否造成交付瓶颈 |

**MVP 范围：** Phase 1-2 无自动度量采集，质量趋势通过人工观察。Phase 3 `sand-measure-light` 就绪后自动关联。

## 质量治理与 HIP 的交互

### 质量检查不通过时的升级路径

| 当前 HIP | 质量检查结果 | 升级行为 |
|---------|------------|---------|
| HIP-1 | L1 自动化检查未通过 | 自动打回 Build，不升级 HIP |
| HIP-1 | L2 AI 检查发现 blocking 问题 | **升级到 HIP-2**，请求人工审查 |
| HIP-2 | L2 AI 检查未通过（非 blocking） | 记录 warning，人工决定是否放行 |
| HIP-2 | L3 人工审查发现安全问题 | **升级到 HIP-3**，全程监督后续修复 |
| HIP-3 | 任何质量检查未通过 | 人工决定处理方式（修复/接受风险/废弃） |

**关键约束：** 质量问题只能触发 HIP **升级**（向更严格的方向），不能触发降级。HIP 降级只能通过信任度积累机制实现（参见 [人类介入模型](../orchestrate/human-intervention.md)）。

**对 SAND 的实践意义：** 质量治理和决策治理通过 HIP 机制紧密耦合。质量问题自动升级 HIP 级别，确保高风险问题不会在低监督级别下被忽略。
