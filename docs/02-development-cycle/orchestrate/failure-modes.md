# AI失败模式分类学

5种失败模式：幻觉生成、上下文遗失、偏见放大、能力越界、级联失败。每种含检测方式和缓解策略。

---

## 概述

AI 失败模式分类学是 SAND 编排阶段子过程 O5 的核心内容。编排方案不仅要定义"如何成功"，更要预见"如何失败"——在编排阶段就为可预期的失败模式设计检测和缓解策略，而不是等到 Validate 阶段才发现问题。

SAND 定义 5 种 AI 原生开发中的典型失败模式。每种失败模式包含：定义、检测信号、缓解策略、影响评级。这些分类直接映射为编排方案中的 `failure_mode_plan` 字段。

**理论基础：**

- **Mikkonen & Taivalsaari (2025)**——[生成式复用风险](../../01-foundations/generative-reuse-risk.md)中的 cargo cult 复用警告：AI 生成的代码可能表面正确但缺乏深度理解支撑
- **Beck, K. (2025)**——Constraint engineering 中的信任模型：将 AI 输出视为"来自不可靠协作者的 PR"（PR from dodgy collaborator）
- **行业实证**——AI 生成代码 bug 率为人工代码的 1.7 倍（CodeRabbit, 2026 [待验证]），安全漏洞含有率 40-62%（多源汇总 [待验证]），81% 的组织对 AI 生成代码存在监控盲区（Sherlock, 2026 [待验证]）

## 五种失败模式

### 1. 幻觉生成（Hallucination） — enum: `hallucination`

**定义：** Agent 生成看似合理但事实错误的输出——不存在的 API、错误的库版本、虚构的配置参数。

| 维度 | 说明 |
|------|------|
| **影响评级** | 高——可能导致运行时错误或安全漏洞 |
| **发生概率** | 中-高——尤其在上下文不足时 |
| **典型场景** | 引用不存在的第三方库函数；生成语法正确但语义错误的代码 |

**检测信号：**
- 引用的 API/库/函数在项目依赖中不存在
- 生成的代码引用不存在的文件路径
- 统计数据或技术细节缺少来源引用
- 验证阶段契约检查项 `must_pass` 失败

**缓解策略：**
- **上下文强化**：确保 Agent 拥有准确的项目依赖列表和 API 文档（O1 上下文工程）
- **交叉验证**：在 Pipeline/Hierarchy 拓扑中引入独立的验证 Agent
- **约束工程**：在意图声明的 `constraints` 中明确技术栈版本
- **HIP 检查**：HIP-2 审查点要求人类确认关键技术决策

---

### 2. 上下文遗失（Context Loss） — enum: `context_loss`

**定义：** Agent 在长会话或多步骤执行中丢失关键上下文信息，导致后续输出与前序决策不一致。

| 维度 | 说明 |
|------|------|
| **影响评级** | 高——可能导致前后矛盾的交付物 |
| **发生概率** | 中——随会话长度和复杂度增加 |
| **典型场景** | Pipeline 后端 Agent 忘记前端的架构决策；长重构中后半段代码风格与前半段不一致 |

**检测信号：**
- Agent 输出与意图声明的 `constraints` 矛盾
- Pipeline 后续步骤产出与前序步骤产出风格/模式不一致
- Agent 重复询问已在上下文中提供的信息
- 有效上下文窗口（MECW）接近饱和

**缓解策略：**
- **上下文分层管理**：按[上下文金字塔](./context-engineering.md)策略选择性加载
- **关键信息前置**：将核心约束放在上下文开头和结尾，避免中间区域（"中间迷失"问题）
- **步骤级上下文刷新**：Pipeline 每步重新加载关键上下文而非依赖继承
- **显式状态传递**：通过 `execution.yaml` 的 `steps_completed` 持久化关键决策

---

### 3. 偏见放大（Bias Amplification） — enum: `bias_amplification`

**定义：** Agent 系统性地偏向某种解决方案、编码风格或技术选择，忽视同样合理的替代方案。

| 维度 | 说明 |
|------|------|
| **影响评级** | 中——可能导致次优但非错误的技术决策 |
| **发生概率** | 中——模型训练数据偏向流行方案 |
| **典型场景** | 默认选择 React 而非评估框架适用性；偏向微服务架构而非评估单体适用场景 |

**检测信号：**
- Agent 推荐方案时未列举替代方案
- 技术选型缺少权衡分析
- 生成的代码过度使用某种设计模式
- 架构对齐检查发现与项目约定不一致

**缓解策略：**
- **Swarm 拓扑**：使用多个 Agent 并行探索不同方案，强制多样性
- **约束声明**：在意图 `constraints` 中明确项目的技术栈偏好
- **审查要求**：HIP-2 审查点要求人类评估技术选型理由
- **反偏见提示**：在上下文中要求 Agent 列举至少 2 个替代方案

---

### 4. 能力越界（Capability Overflow） — enum: `capability_overflow`

**定义：** Agent 尝试执行超出其能力范围的任务——如代码生成 Agent 尝试做架构决策，或单一 Agent 处理需要多专业协作的任务。

| 维度 | 说明 |
|------|------|
| **影响评级** | 高——可能产出表面完整但质量低下的工件 |
| **发生概率** | 中——尤其在 Solo 拓扑处理复杂任务时 |
| **典型场景** | FDE+ Agent 做组织级成熟度评估；代码生成 Agent 设计数据库架构 |

**检测信号：**
- 任务范围超出 Agent 能力卡的 `capability_domain`
- Agent 输出质量随任务复杂度增加显著下降
- Agent 在某些子任务上频繁"跳过"或给出模糊回答
- 上下文窗口需求超出 Agent 的 `context_window_need`

**缓解策略：**
- **能力卡匹配**：O2 选型阶段严格按[能力卡](./agent-selection.md)匹配，不让 Agent 执行超出声明能力的任务
- **拓扑升级**：检测到能力越界时，从 Solo 升级到 Pipeline 或 Hierarchy，引入专业 Agent
- **`known_limitations` 检查**：在编排阶段检查任务是否命中 Agent 的已知局限
- **快速失败**：Agent 应在识别到能力不足时主动报告，而非勉强输出

---

### 5. 级联失败（Cascade Failure） — enum: `cascade_failure`

**定义：** 一个 Agent 的错误输出被后续 Agent 接受并放大，错误沿执行链传播，最终产生严重偏差。

| 维度 | 说明 |
|------|------|
| **影响评级** | 极高——可能导致整个执行链的产出无效 |
| **发生概率** | 低-中——主要在 Pipeline 和 Hierarchy 拓扑中 |
| **典型场景** | 设计 Agent 输出错误架构 → 实现 Agent 按错误架构编码 → 测试 Agent 为错误代码编写通过的测试 |

**检测信号：**
- Pipeline 后续步骤的偏差事件数量递增
- 多个步骤的验证结果指向同一个根因
- Agent 间传递的中间产物与意图声明偏差度逐步增大
- Validate 阶段三通道同时失败

**缓解策略：**
- **中间验证点**：在 Pipeline 的关键交接处插入验证步骤
- **HIP 审查**：在 Pipeline 每步输出处设置 HIP-2 审查点（高风险任务）
- **独立验证 Agent**：引入不参与执行的独立验证 Agent（Critic 角色）
- **回滚机制**：执行引擎的断点续传（`steps_completed`）支持回滚到最后正确步骤
- **意图对齐检查**：每步输出与原始意图声明做对齐度比对

## 失败模式与拓扑关联矩阵

不同拓扑对不同失败模式的敏感度不同：

| 失败模式 | Solo | Pipeline | Swarm | Hierarchy |
|---------|------|----------|-------|-----------|
| **幻觉生成** | 高风险——无交叉验证 | 中风险——后续步骤可能检测 | 低风险——多 Agent 可交叉验证 | 中风险——管理者可能传播 |
| **上下文遗失** | 低风险——单一上下文 | 高风险——长链条衰减 | 中风险——并行上下文分叉 | 高风险——层级间传递损失 |
| **偏见放大** | 高风险——单一视角 | 中风险——单一路径 | 低风险——多视角对冲 | 中风险——管理者偏见传播 |
| **能力越界** | 高风险——无专业分工 | 低风险——步骤专业化 | 中风险——聚合器可能越界 | 低风险——角色明确分工 |
| **级联失败** | N/A——无链条 | 高风险——线性传播 | 低风险——独立并行 | 高风险——层级传播 |

**选型启示：**
- Solo 拓扑需要重点防范幻觉、偏见和能力越界
- Pipeline 拓扑需要重点防范上下文遗失和级联失败
- Swarm 拓扑在失败模式防范上整体最优，但聚合复杂度高
- Hierarchy 拓扑需要重点防范管理者引起的级联失败和上下文遗失

## 编排层防御机制设计原则

### 原则一：早期检测（Early Detection）

在编排阶段（而非执行或验证阶段）就识别潜在失败风险：
- 意图声明的 `constraints` 是否足以约束幻觉？
- 选定的拓扑是否与任务的风险特征匹配？
- Agent 能力卡是否覆盖所有子任务？

### 原则二：快速失败（Fail Fast）

执行过程中检测到失败信号时立即停止，而非继续执行：
- Pipeline 中某步输出不通过中间验证 → 停止链条执行
- Agent 报告能力不足 → 升级拓扑或更换 Agent
- 上下文窗口接近饱和 → 暂停并重新评估上下文策略

### 原则三：优雅降级（Graceful Degradation）

失败不等于灾难——设计降级路径而非全面中断：
- 级联失败 → 回滚到最后正确步骤并从该点重新执行
- 能力越界 → 将超出部分标记为待人工处理
- 上下文遗失 → 从持久化状态重建关键上下文

## 与 Validate 阶段的关系

失败模式分类学是 Validate 阶段[三通道验证](../validate/three-channel.md)设计的理论依据之一：

| 失败模式 | 对应验证通道 | 检测机制 |
|---------|-----------|---------|
| 幻觉生成 | 契约验证通道 | `must_pass` 条目验证 Agent 输出的事实正确性 |
| 上下文遗失 | 契约验证通道 | 意图对齐度分析检测输出与意图的偏差 |
| 偏见放大 | 架构对齐通道 | 架构模式一致性检查防止偏离项目约定 |
| 能力越界 | 架构对齐通道 + 安全通道 | 代码复用检查 + 依赖安全性检查 |
| 级联失败 | 三通道综合 | 三通道同时失败是级联失败的强信号 |

## 对 SAND 的实践意义

失败模式分类学将"AI 可能出错"从模糊担忧转化为**可预防、可检测、可缓解的工程实践**：

1. **预防优先**：在编排阶段设计 `failure_mode_plan`，而非事后修补
2. **拓扑选择的安全维度**：拓扑选型不仅考虑效率，还要考虑对应的失败模式风险
3. **与 HIP 联动**：高风险失败模式（幻觉、级联）需要更高 HIP 级别的人类审查
4. **审计可追溯**：失败事件通过偏差追踪（deviation tracking）记录在审计链中

SAND 的失败模式分类学借鉴了 Beck 的**信任模型**——AI 输出不是"正确或错误"的二元判断，而是需要与人类工程师的"不可靠协作者 PR"一样经过系统性审查。
