# 运营信号采集

四类信号（业务/技术/AI 行为/异常）构成 Operate 阶段的数据基座。`sand-measure-light` 从中选取 5 个轻量信号，基于 ADR-007 原则以 Skill 内嵌脚本实现零基础设施采集。

---

## 概述

传统运营监控关注"系统是否健康"；SAND Operate 阶段关注的是更深层的问题：**AI 辅助开发是否真正在提升团队的工程效能，还是制造了被掩盖的风险？**

这个问题之所以难回答，是因为传统软件度量在 AI 参与的开发中已经失效（参见 [非确定性编程范式 §失效度量分析](../../01-foundations/non-deterministic-paradigm.md#失效度量分析)）。代码行数、覆盖率、PR 合并速度等指标在 AI 可以秒级生成代码的世界里不再反映真实的工程能力。

SAND 的应对策略是：**重新选择信号源**。不测量"产出了多少"，而测量"产出的质量如何"和"团队的学习是否在加速"。

---

## 四类运营信号

Operate 阶段定义 4 类信号，覆盖生产环境的完整观测面：

| 类别 | 关注点 | 信号示例 | 流向 |
|------|--------|---------|------|
| **业务信号** | 用户行为与业务价值 | 转化率、用户留存、功能使用率 | → Learn 阶段（投资假设验证） |
| **技术信号** | 系统性能与交付效率 | PR 周期时间、部署频率、变更失败率 | → Learn + Assess（效率基线） |
| **AI 行为信号** | AI 参与深度与决策质量 | AI 参与度、AI 生成代码审查通过率 | → Learn（认知债务预警） |
| **异常信号** | 事故与异常模式 | 事故标签、异常检测告警 | → Learn（失败案例库补充） |

全部信号最终流入 Learn 阶段，作为复盘和资产化的数据输入。

## sand-measure-light 5 个轻量信号

`sand-measure-light`（FR34-FR37）不尝试采集全部信号。它从 4 类信号中选取 5 个**低摩擦、高信噪比**的轻量信号，满足 ADR-007"零基础设施"约束。

### 信号选择依据

选择标准：

1. **数据可及性** — 仅依赖 Git CLI 和 CI API（或 CSV fallback），不引入额外监控工具
2. **信号有效性** — 该信号在 AI 参与的开发中仍然保持信号价值（未被 AI 生产力膨胀扭曲）
3. **行动可指导性** — 信号的异常方向可以直接关联到具体的改善行动
4. **认知失调潜力** — 能够揭示团队"自我感觉良好"与"客观数据恶化"之间的落差（PRD §Journey 4 吴芳）

### 与失效度量分析表的关系

[非确定性编程范式 §失效度量分析](../../01-foundations/non-deterministic-paradigm.md#失效度量分析) 定义的是**战略层 AI 原生替代信号**——回答"传统度量失效后，SDC 框架用什么替代"（如意图首通率替代 PR 合并速度、变更失败率替代 Bug 修复时间）。这些信号依赖 `.sand/` 意图/验证数据，主要在 Intent、Validate、Learn 阶段采集。

`sand-measure-light` 的 5 个信号属于**运营层可采集信号**——回答"Operate 阶段能从 Git/CI 零基础设施采集什么"（PR 周期时间、部署频率等）。两者处于不同抽象层级，互补而非互斥：

| 层级 | 关注点 | 典型信号 | 采集时机 |
|------|--------|---------|---------|
| **战略层** | SDC 循环质量与 AI 协作效能 | 意图首通率、契约验证通过率、偏差事件频率 | Intent / Validate / Learn |
| **运营层** | 生产交付节奏与 AI 参与可见性 | PR 周期时间、变更失败率、AI 参与度 | Operate（Git/CI） |

下表将 5 个运营信号与失效度量分析表中的传统度量及战略层替代信号建立交叉引用，避免误读为"一一替代"：

| 运营信号 | 关联的失效传统度量 | 战略层 AI 原生替代（范式表） | 关系说明 |
|---------|------------------|---------------------------|---------|
| PR 周期时间 | PR 数量/合并速度 | 意图首通率 | 运营层捕捉审查瓶颈；战略层衡量意图一次性质量 |
| 事故标签 | Bug 修复时间 | 变更失败率、偏差事件频率 | 运营层分类 AI 相关根因；战略层衡量交付可靠性 |
| AI 参与度 | 代码行数（LoC） | 意图声明完成率、SDC 循环完成率 | 运营层追踪 AI 采纳深度；战略层衡量意图驱动产出 |
| 变更失败率 | Bug 修复时间 | 变更失败率 | 运营层与战略层一致——DORA 结果度量在 AI 时代仍有效 |
| 部署频率 | —（DORA 度量仍有效） | — | 独立有效的交付节奏信号，需与变更失败率联合解读 |

各信号定义中的"关联的失效传统度量"指该运营信号所**观测的同一失效维度**，而非声称直接替代战略层信号。

### 信号 1：PR 周期时间（PR Cycle Time）

- **分类：** 技术信号
- **定义：** 从首次提交到合并的时长中位数
- **选择依据：** 行业报告（Pragmatic Engineer 2025）显示 AI 使 PR 产量翻倍但审查时间显著增长——PR 周期时间捕捉了这个"快产出 vs 慢审查"的张力
- **数据源：** Git 提交历史
- **采集方法：** `git log --merges` 解析合并提交时间 vs 首次提交时间
- **计算公式：** `median(merge_timestamp - first_commit_timestamp)` 取最近 N 个 PR
- **健康范围：** 团队规模依赖；关注趋势方向（持续增长 = 审查瓶颈）
- **关联的失效传统度量：** PR 数量/合并速度（已失效——AI 膨胀了 PR 产量）；战略层替代见 [意图首通率](../../06-metrics/quality-metrics.md#意图首通率intent-first-pass-rate)

### 信号 2：事故标签（Incident Labels）

- **分类：** 异常信号
- **定义：** 生产事故按根因分类的标签统计，区分 AI 相关与非 AI 相关
- **选择依据：** AI 生成代码的事故根因分布揭示了约束工程（Harness Engineering）的有效性——AI 相关事故占比上升意味着验证通道需要加强
- **数据源：** Incident tracking 系统（Jira/PagerDuty/手动记录）
- **采集方法：** CI API 读取事故标签；无 API 时接受 CSV 手动导入（FR36）
- **分类方法：** `ai_related`（AI 生成代码为根因）/ `non_ai`（传统 bug）/ `mixed`（AI 和人类代码交互导致）
- **健康范围：** `ai_related` 占比趋势——稳定或下降为健康，持续上升需干预
- **关联的失效传统度量：** Bug 修复时间（已失效——AI 快速"修复"可能引入新隐性问题）；战略层替代见 [变更失败率](../../06-metrics/quality-metrics.md#变更失败率change-failure-rate)

### 信号 3：AI 参与度（AI Involvement Rate）

- **分类：** AI 行为信号
- **定义：** 代码变更中 AI 辅助生成的占比
- **选择依据：** 追踪团队的 AI 协作深度——既检测"AI 工具闲置"（采纳度不足），也预警"过度依赖"（认知债务风险，参见 Fowler 2026 认知债务警告）
- **数据源：** Git commit history
- **采集方法：** 基于 commit message 特征（如 `Co-Authored-By: *AI*`、`🤖`、IDE 插件标记）或 author 标签检测
- **计算公式：** `count(ai_assisted_commits) / count(all_commits)` 取最近 N 天
- **健康范围：** 无绝对基准；关注与团队成熟度维度的联动（高 AI 参与度 + 低人类审查体系 = 认知债务风险）
- **关联的失效传统度量：** 代码行数（已失效——AI 秒级生成数千行）；战略层替代见 [意图吞吐量](../../06-metrics/efficiency-metrics.md#意图吞吐量intent-throughput)

### 信号 4：变更失败率（Change Failure Rate）

- **分类：** 技术信号
- **定义：** 导致生产环境服务降级或需要回滚的变更占总变更的比例
- **选择依据：** DORA 四关键度量之一，在 AI 时代仍然有效——它测量的是*结果*（生产是否出问题）而非*过程*（代码怎么写的）
- **数据源：** CI/CD pipeline + incident tracking
- **采集方法：** CI API 获取部署事件；关联事故记录判定失败变更
- **计算公式：** `count(failed_changes) / count(all_changes)` 取最近 N 个部署周期
- **健康范围：** DORA 基准——Elite: 0-5%, High: 6-15%, Medium: 16-30%, Low: >30%
- **关联的失效传统度量：** 静态分析得分（已失效——AI 代码可能通过静态分析但存在语义级问题）；战略层替代见 [验证决策矩阵](../validate/decision-matrix.md)

### 信号 5：部署频率（Deployment Frequency）

- **分类：** 技术信号
- **定义：** 向生产环境部署的频率
- **选择依据：** DORA 四关键度量之一，反映团队的交付节奏和持续交付能力；与变更失败率联动分析可揭示"快但不稳"的模式
- **数据源：** CI/CD pipeline
- **采集方法：** CI API 获取部署事件时间线
- **计算公式：** `count(deployments) / time_window`（如 每天/每周/每月）
- **健康范围：** DORA 基准——Elite: 按需/每天多次, High: 每天~每周, Medium: 每周~每月, Low: 每月~每半年
- **关联的失效传统度量：** 无直接对应（DORA 度量在 AI 时代仍然有效，但需与变更失败率联合解读）

## 采集架构（ADR-007）

**架构决策：** 轻量度量用 Skill 内嵌脚本实现，不引入独立采集服务。

**核心约束：**

- **零基础设施** — `git clone` + AI IDE 即全部所需，无需部署监控服务
- **棕地集成低摩擦** — 任何有 `git` + `curl`（或手动 CSV）的环境即可运行
- **性能约束** — 典型规模 Git 仓库 5 分钟内完成全部采集（NFR18）
- **平台无关** — 不依赖特定 CI 平台 SDK（NFR9）

**采集工具分工：**

| 工具 | 采集信号 | 依赖 |
|------|---------|------|
| `git-metrics.py` | PR 周期时间、AI 参与度 | Git CLI（`git log`） |
| `ci-metrics.py` | 变更失败率、部署频率、事故标签 | cURL/HTTP 客户端 + CI API |
| CSV 手动导入 | 全部 5 个信号的 fallback | 无（FR36 fallback 机制） |

**输出格式：** `.sand/metrics/{date}_metrics.json`

## 应用场景：认知失调驱动变革

度量数据的最终目标不是"生成报告"，而是**制造认知失调**——用数据揭示团队"自我感觉良好"与"客观数据恶化"之间的落差，推动渐进变革。

**典型应用（PRD §Journey 4 吴芳）：**

- "PR 合并量是去年的 3 倍（好事），但 PR 审查中位时间从 1.5 天涨到 7 天（坏事）" → **PR 周期时间**信号
- "上季度 3 次生产事故中，2 次的根因是 AI 生成的代码未经充分审查" → **事故标签**信号
- "4 个团队各自开发了类似的认证中间件，没有任何复用" → **AI 参与度** + 飞轮指标联动

sand-measure-light 的 `step-02-report.md` 将上述数据转化为结构化的认知失调报告（FR37），包含正向指标、负向指标、变化趋势分析和推荐的下一步行动。
