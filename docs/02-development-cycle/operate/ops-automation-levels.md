# 三级运营自动化

OPS-1（AI 自主处理）、OPS-2（AI 建议 + 人工执行）、OPS-3（AI 信息 + 人工决策）三级渐进自动化模型。新规则从 OPS-2 起步，积累信任后升级为 OPS-1；异常时降级回 OPS-3。

---

## 概述

AI 原生运营的核心挑战不是"AI 能否自动化运维操作"——答案显然是肯定的。真正的挑战是：**在多大范围内允许 AI 自主行动，何时必须保留人类决策权？**

SAND 的回答是三级运营自动化模型（OPS-1/2/3），它为每一类运营操作定义了明确的 AI 行为边界和人类行为边界。这个模型的设计哲学与 SAND 的约束工程（Harness Engineering）思想一脉相承：**不是限制 AI 的能力，而是根据操作的风险等级和组织的信任积累程度，渐进地扩大 AI 的自主范围。**

---

## 三级定义

### OPS-1：AI 自主处理

> 已知问题 + 标准修复 → AI 全程自动化，人类事后审阅日志

**AI 行为边界：**
- 自动检测已知模式的异常（基于失败案例库匹配）
- 自动执行预定义的修复方案（如重启服务、清理缓存、回滚到上一个稳定版本）
- 自动记录操作日志和审计事件到 `.sand/audits/audit.jsonl`
- 操作完成后自动验证修复效果

**人类行为边界：**
- 事后审阅操作日志（确认 AI 操作的合理性）
- 定期审查 OPS-1 操作的累计效果
- 可随时将特定操作降级为 OPS-2

**典型场景：**
- 已知的内存泄漏模式 → 自动重启受影响服务
- CI pipeline 因暂时性网络问题失败 → 自动重试
- 度量采集脚本执行 → `sand-measure-light` 的 `git-metrics.py` 和 `ci-metrics.py` 自动运行
- 审计日志轮转 → 自动归档旧日志文件

**准入条件：** 该操作类型已在 OPS-2 运行 ≥3 次且无人工否决记录。

### OPS-2：AI 建议 + 人工执行

> 中等风险操作 → AI 分析根因并生成方案，人类审查后批准执行

**AI 行为边界：**
- 分析问题的根因（日志分析、错误模式匹配、影响范围评估）
- 生成 1-3 个修复方案（含每个方案的预期效果、风险和回滚策略）
- 准备执行脚本或命令（但不自动执行）
- 记录分析过程和推荐理由

**人类行为边界：**
- 审查 AI 的根因分析是否正确
- 从推荐方案中选择或修改后批准
- 确认执行并监控效果
- 决定是否将该操作升级为 OPS-1 或降级为 OPS-3

**典型场景：**
- 性能下降但原因不明 → AI 分析瓶颈并推荐优化方案，人工确认后执行
- 依赖库安全漏洞通知 → AI 评估影响范围并生成升级计划，人工审批
- 新的部署配置变更 → AI 生成变更方案和回滚预案，人工确认后部署
- 新增的度量采集规则 → 首次运行需人工确认数据准确性

**默认级别：** 所有新引入的运营操作默认从 OPS-2 开始。

### OPS-3：AI 信息 + 人工决策

> 高风险事件 → AI 提供数据和分析，人类独立判断和决策

**AI 行为边界：**
- 收集和整理相关数据（日志、度量、历史事件）
- 提供信息摘要和初步分析
- 列出可能的行动方向（不推荐具体方案）
- 记录人类决策过程（供后续学习）

**人类行为边界：**
- 独立判断问题的严重程度和影响范围
- 制定处理方案和执行计划
- 全程主导执行过程
- 事后将处理方案纳入失败案例库（为未来升级到 OPS-2/1 积累知识）

**典型场景：**
- 首次出现的未知生产事故 → AI 收集日志和影响数据，人类判断处理优先级和方案
- 数据一致性异常 → AI 展示差异分析，人类决定修复策略
- 大规模架构变更的运营影响 → AI 提供历史数据参考，人类制定迁移计划
- 合规审计中发现的运营风险 → AI 整理相关证据，人类制定整改方案

**降级触发：** 异常结果触发降级（具体规则见下方降级路径表）。

## 级别升降规则

### 升级路径（信任积累）

```
OPS-3 ──→ OPS-2 ──→ OPS-1
 │            │            │
 │   人类处理方案    AI方案被人工     AI自动操作
 │   纳入案例库     批准≥3次         无人工否决
 │            │            │
 └── 首次遇到 ── 模式已知 ── 充分验证 ──┘
```

**升级条件：**

| 从 | 到 | 条件 |
|----|-----|------|
| OPS-3 → OPS-2 | AI 建议 | 该问题模式已在 OPS-3 中被人工处理 ≥1 次，处理方案已记录到失败案例库 |
| OPS-2 → OPS-1 | AI 自主 | 该操作类型已在 OPS-2 运行 ≥3 次，人工批准率 100%（无否决，参见下方否决追踪机制），修复效果验证通过 |

### 否决追踪机制

OPS 升级条件中的"无否决"需要可审计的追踪记录。否决（Veto）指人工在 OPS-2 阶段拒绝 AI 推荐的修复方案，或将 OPS-1 自动操作降级为人工处理。

| 维度 | 定义 |
|------|------|
| **发起者** | 对该操作类型有审批权限的运维负责人或值班工程师（与 HIP-2 审批人角色一致） |
| **触发场景** | OPS-2 方案审查后拒绝执行；OPS-1 自动操作被人工中断或事后标记为不当 |
| **记录方式** | 写入 `.sand/audits/audit.jsonl`，`event_type` 为 `ops_veto`，包含 `operation_type`（操作类型标识）、`ops_level`（当前级别）、`veto_reason`（否决原因）、`operator`（否决人） |
| **存储位置** | `.sand/audits/audit.jsonl`（与 OPS-1 操作日志同一审计流） |
| **查询用途** | 升级判定：统计某 `operation_type` 在 OPS-2 阶段的否决次数；降级判定：单次否决即触发 OPS-2 → OPS-3 降级 |

**示例审计事件字段：**

```json
{
  "event_type": "ops_veto",
  "operation_type": "ci-pipeline-retry",
  "ops_level": "OPS-2",
  "veto_reason": "根因分析不完整，需人工排查网络配置",
  "operator": "on-call-engineer"
}
```

### 降级路径（异常触发）

| 触发条件 | 降级动作 |
|---------|---------|
| OPS-1 自动修复后验证失败 | 该操作类型降级至 OPS-2 |
| OPS-2 方案被人工否决 | 该操作类型降级至 OPS-3 |
| 连续 2 次 OPS-1 操作触发新问题 | 该操作类型降级至 OPS-3 + 全面审查 |
| 安全事件涉及 OPS-1 自动操作 | 所有相关 OPS-1 冻结至 OPS-3 直到审查完成 |

**"新问题"操作化定义：** 在 OPS-1 自动操作完成后的验证窗口（默认 24 小时）内，出现以下任一情况，且该情况在操作前不存在：

1. **生产服务降级** — 可用性指标下降、错误率上升或 SLA 违反
2. **安全事件** — 与自动操作直接相关的权限越界、数据泄露或合规违规
3. **级联故障** — 自动操作引发的其他系统组件异常（因果关联由事后审查确认）

不满足上述条件的问题（如操作前已存在的已知缺陷、与操作无因果关联的独立事件）不计入"新问题"。连续 2 次指同一 `operation_type` 在两次独立的 OPS-1 执行中各自触发一次新问题。

### 信任重置

团队变动（核心成员变更 >30%）或技术栈重大升级时，建议将所有 OPS-1 操作重置为 OPS-2，重新积累信任基线。

## 与 HIP 机制的映射

OPS-1/2/3 与 HIP-1/2/3（Human Intervention Protocol，参见 [人类介入协议](../orchestrate/human-intervention.md)）是**互补而非替代**的两套控制机制：

| 维度 | HIP（编排阶段） | OPS（运营阶段） |
|------|----------------|----------------|
| **控制对象** | Skill 编排中的认知决策 | 生产环境中的运维操作 |
| **决策类型** | "做什么"——意图确认、拓扑选型 | "怎么修"——故障修复、配置变更 |
| **风险评估时机** | 执行前（前置审查） | 执行中/后（实时响应） |
| **适用阶段** | SDC 循环的 Orchestrate 阶段 | SDC 循环的 Operate 阶段 |

**对应关系：**

| HIP 级别 | OPS 级别 | 共同特征 |
|---------|---------|---------|
| HIP-1（全自主） | OPS-1（AI 自主处理） | AI 全程自主，人类事后审阅 |
| HIP-2（关键决策审查） | OPS-2（AI 建议 + 人工执行） | AI 分析推荐，人类关键审批 |
| HIP-3（全程监督） | OPS-3（AI 信息 + 人工决策） | AI 辅助信息，人类主导决策 |

**关键区别：** HIP 的级别由 Skill 的 `human_oversight` 字段静态声明（设计时确定）；OPS 的级别是动态的——同一操作随信任积累可以升级，异常时自动降级。

## 与 sand-measure-light 的关系

`sand-measure-light` 的度量采集操作属于 **OPS-1** 级别：

- 已知模式：从 Git/CI 读取数据并输出 JSON 是确定性操作
- 标准流程：`git-metrics.py` 和 `ci-metrics.py` 执行预定义的采集逻辑
- 低风险：只读操作，不修改任何系统状态
- 审计可追溯：采集结果持久化到 `.sand/metrics/{date}_metrics.json`

但度量数据的**解读和行动建议**（认知失调报告）属于 **OPS-2** 级别——AI 生成分析报告和推荐行动，但最终决策由人类（变革催化师/技术负责人）做出。
