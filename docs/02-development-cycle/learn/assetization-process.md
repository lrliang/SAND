# 资产化流程

4 步精炼：L2a 候选识别（AI 自动扫描）→ L2b 人工评审 → L2c 结构化（标准格式 + 元数据）→ L2d 注册入库（版本化 + 过期审查周期）。

---

## 概述

资产化流程是将复盘发现（参见 [AI 复盘标准议程](./ai-retrospective.md)）转化为可复用 AI 资产（参见 [AI 资产分类学](./ai-asset-taxonomy.md)）的标准化精炼过程。

### 为什么是 4 步而非直接入库

资产化采用 4 步精炼而非"AI 识别后直接入库"，基于两个核心原则：

1. **质量门控**：AI 识别的模式可能存在过拟合（仅在特定上下文中有效）、幻觉（看到实际不存在的模式）或时效性问题。无门控的直接入库会导致资产库质量快速退化。

2. **人类审查不可削减**：根据 Mikkonen 的生成式复用风险理论（参见 [生成式复用风险](../../01-foundations/generative-reuse-risk.md)），AI 自动提取的"知识"与 Cargo Cult 编程中的"不理解的代码复制"在认知结构上同构——L2b 人工评审是打破这一认知断裂的唯一手段。跳过人工评审的资产化流程，本质上是在建设一个"Cargo Cult 知识库"。

## 流程全貌

```
复盘产出（asset_candidates）
    │
    ▼
  ┌─────────────┐
  │ L2a 候选识别 │ ← AI 自动扫描复盘日志和执行数据
  └─────┬───────┘
        │ 候选清单
        ▼
  ┌─────────────┐
  │ L2b 人工评审 │ ← 人类判断：接受 / 拒绝 / 修改后接受
  └─────┬───────┘
        │ 已审核候选
        ▼
  ┌─────────────┐
  │ L2c 结构化   │ ← 转化为标准格式 + 填充元数据
  └─────┬───────┘
        │ 结构化资产
        ▼
  ┌─────────────┐
  │ L2d 注册入库 │ ← 版本化 + 关联关系 + 过期审查周期
  └─────────────┘
        │
        ▼
  资产库（Git 仓库中的资产目录，Phase 3 实现时定义具体路径）
```

## 步骤 L2a：候选识别

**执行者：** AI（sand-run-retrospective Skill 自动执行）
**输入：** 复盘日志（`.sand/retrospectives/{date}_retro.md`）+ 执行数据（`.sand/` 目录）
**输出：** 候选清单（`asset_candidates` YAML 列表）

### 扫描维度

AI 从以下三个维度扫描可资产化的模式：

| 扫描维度 | 数据源 | 识别标准 |
|---------|--------|---------|
| **重复出现的模式** | 多轮复盘日志对比 | 相同或相似的发现在 ≥2 轮复盘中出现 |
| **高效率片段** | 执行数据（意图首通率、执行时长） | 显著优于平均水平的执行实例 |
| **失败模式** | `audit.jsonl` failure 事件 + `deviations.json` | status=failure/interrupted 的结构化事件 |

### 候选输出格式

```yaml
asset_candidates:
  - candidate_id: "CAN-20260515-001"
    asset_type: "intent_pattern"
    source_topic: "intent_quality"
    source_intent_id: "INT-20260512-003"
    description: "多租户功能的意图声明模板——含安全约束和性能基线"
    expected_reuse_frequency: "high"
    expected_shelf_life: "medium"
    confidence: 0.7
    evidence:
      - "3 轮循环中类似意图的 CLEAR 首通率从 40% 提升到 85%"
      - "使用此模式后验证偏差数下降 60%"
```

### 扫描约束

- 候选数量不设硬上限，但建议每轮复盘产出 3-10 个候选（过多表明扫描粒度过细）
- 每个候选必须关联至少一条 evidence（证据）
- 初始 confidence 基于证据强度估算：单次观察 0.3-0.5，多次观察 0.5-0.7，量化数据支持 0.7-0.9

## 步骤 L2b：人工评审

**执行者：** 人类（FDE+ 或技术负责人）
**输入：** L2a 产出的候选清单
**输出：** 已审核候选（标注评审决策）

### 为什么不可省略

Mikkonen 的 Cargo Cult 理论（参见 [生成式复用风险](../../01-foundations/generative-reuse-risk.md)）指出：AI 提取的模式可能在表面上正确但在语义上存在偏差——与 AI 生成的代码"看起来对但不理解为什么对"是同一种认知风险。人工评审提供了三个不可替代的功能：

1. **准确性验证**：AI 识别的模式是否确实存在，还是过拟合/幻觉
2. **通用性判断**：模式是否在当前上下文之外也有效，还是仅在特定条件下成立
3. **时效性判断**：模式是否仍然有效，还是基于已过时的技术/业务背景

### 评审标准

| 评审维度 | 通过标准 | 拒绝标准 |
|---------|---------|---------|
| **准确性** | 模式与实际执行数据一致，证据链完整 | 证据不足或存在矛盾 |
| **通用性** | 适用于类似场景的多个实例 | 仅在单一特殊情况下有效 |
| **时效性** | 基于当前有效的技术栈和业务规则 | 基于已弃用的技术或已变更的业务规则 |

### 评审决策

| 决策 | 标识 | 后续动作 |
|------|------|---------|
| **接受** | `accepted` | 进入 L2c 结构化 |
| **拒绝** | `rejected` | 记录拒绝原因，不进入资产库 |
| **修改后接受** | `accepted_with_changes` | 评审者标注修改建议，AI 协助修改后进入 L2c |

### 评审记录

```yaml
review:
  reviewer: "reviewer_name"
  reviewed_at: "ISO-8601 UTC"
  decision: "accepted"
  notes: "评审意见（如有修改建议）"
```

## 步骤 L2c：结构化

**执行者：** AI + 人类协作（AI 生成初稿，人类确认）
**输入：** 已审核通过的候选
**输出：** 符合标准格式的结构化资产文件

### 标准元数据填充

每个资产必须包含完整的元数据字段（参见 [AI 资产分类学 §标准元数据](./ai-asset-taxonomy.md#标准元数据结构)）：

| 字段 | 填充规则 |
|------|---------|
| `asset_id` | 自动生成：`AST-{type_code}-{YYYYMMDD}-{seq}` |
| `asset_type` | 从候选的 `asset_type` 继承 |
| `version` | 初始版本 `1.0.0` |
| `confidence` | 从候选的 `confidence` 继承，经评审可调整 |
| `source_intent_id` | 从候选继承（如适用） |
| `source_retro_date` | 复盘日期 |
| `created_at` | 当前时间 |
| `expires_at` | 基于资产类型的默认过期周期计算 |
| `tags` | AI 提取关键词 + 人类补充 |
| `created_by` | `ai+human`（AI 结构化 + 人类评审） |

### 内容格式化

资产内容按对应类型的标准格式（参见 [AI 资产分类学](./ai-asset-taxonomy.md)）填充。关键要求：

- 使用 2 空格缩进的 YAML 格式
- 所有值使用 `true`/`false`、`null`（不用 `yes`/`no`/`~`）
- 字符串中的技术术语保持英文原形
- 代码示例使用标准代码块格式

## 步骤 L2d：注册入库

**执行者：** AI（自动化）+ 人类确认
**输入：** 结构化资产文件
**输出：** 注册到资产库的资产 + 关联关系

### 版本化策略

- 新资产初始版本 `1.0.0`
- 内容微调（措辞修改、格式优化）：`1.0.x`（Patch）
- 实质性更新（新增检查项、修改预防策略）：`1.x.0`（Minor）
- 根本性变更（资产类型重分类、适用范围重新定义）：`x.0.0`（Major）

### 过期审查周期

| 资产类型 | 默认过期周期 | 理由 |
|---------|------------|------|
| 上下文资产 | 90 天 | 技术栈和架构变化较频繁 |
| 意图模式 | 180 天 | 业务模式变化周期较长 |
| 编排配方 | 120 天 | Skill 生态和工具链变化 |
| 验证规则 | 180 天 | 安全规则需定期审查但变化频率中等 |
| 失败案例 | 365 天 | 失败教训通常长期有效 |

过期不意味着自动删除，而是触发人工审查决策：**刷新**（更新内容并重置过期时间）、**归档**（移入历史记录）、**延期**（确认仍有效并延长过期时间）。

### 关联关系建立

入库时建立资产间的关联关系：

- **依赖关系**：此资产依赖哪些其他资产（如验证规则依赖的上下文资产）
- **被依赖关系**：哪些资产依赖此资产
- **相关关系**：语义相关但无依赖的资产（如同一领域的不同类型资产）

## 触发关系

| 触发条件 | 触发者 | 输出位置 |
|---------|--------|---------|
| Learn 阶段末尾（每轮 SDC 循环） | `sand-run-retrospective` Skill | `.sand/retrospectives/` |
| 资产候选清单产出后 | 人工评审者 | 资产库目录 |
| Phase 2（基础版） | 仅 L2a 自动扫描 + 结构化日志输出 | `.sand/retrospectives/` |
| Phase 3（完整版） | 完整 L2a-L2d 流程 | Git 仓库中的资产目录 |

**Phase 2 → Phase 3 演进路径：** Phase 2 的 `sand-run-retrospective` 基础版仅执行到"候选识别"（L2a），将候选清单写入结构化日志。L2b-L2d 在 Phase 3 完整版中实现，届时复盘 Skill 将引导完整的 4 步资产化流程。

**对 SAND 的实践意义：** 资产化流程的 4 步设计体现了 SAND 的核心哲学——人类判断不可省略。AI 擅长从大量数据中识别模式（L2a），但判断模式是否真正有价值、是否可推广、是否仍然有效，需要人类的认知参与（L2b）。这不是对 AI 能力的不信任，而是对生成式复用风险的系统性应对。
