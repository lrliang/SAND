# 资产质量与生命周期

衰减/刷新机制的置信度模型（使用+通过 +0.05，使用+不适用 -0.10，长期未用按类型缓慢衰减），版本化管理（创建来源、变更历史、使用记录、关联关系）。置信度范围 0.0-1.0，低于 0.4 触发审查。

---

## 概述

AI 资产不是"写完就不管"的静态文档。在 AI 原生开发的非确定性环境中（参见 [非确定性编程范式](../../01-foundations/non-deterministic-paradigm.md)），知识的时效性面临三重挑战：

1. **技术栈演进**：框架升级、库版本变更使上下文资产过时
2. **业务规则变化**：需求迭代使意图模式和验证规则失效
3. **AI 能力进化**：模型能力提升使某些失败模式不再适用

资产生命周期管理通过状态机、置信度模型和版本化机制，确保资产库中的每个资产在被消费时仍然有效。

## 生命周期状态机

### 状态定义

```
  ┌──────────┐   L2d 入库    ┌────────┐   过期/衰减    ┌─────────────┐
  │ Candidate │ ───────────→ │ Active │ ────────────→ │ Deprecated  │
  └──────────┘               └────────┘               └─────────────┘
       │                       ↑    │                       │
       │ L2b 拒绝               │    │ 置信度低于阈值         │ 确认无效
       ▼                       │    ▼                       ▼
  ┌──────────┐            刷新  │  ┌─────────────┐     ┌──────────┐
  │ Rejected │                 └──│ Under Review│     │ Archived │
  └──────────┘                    └─────────────┘     └──────────┘
```

| 状态 | 含义 | 进入条件 | 退出条件 |
|------|------|---------|---------|
| **Candidate** | 由 L2a 识别的候选 | 复盘议题 5 产出 | L2b 评审通过 → Active；拒绝 → Rejected |
| **Active** | 可被 Skill 消费的有效资产 | L2d 注册入库 | 过期触发审查 → Under Review；置信度低于阈值 → Under Review |
| **Under Review** | 过期或衰减触发的审查中状态 | 过期时间到达或置信度低于阈值 | 刷新 → Active；确认失效 → Deprecated |
| **Deprecated** | 已知不再有效但保留历史参考 | 审查确认失效 | 归档 → Archived |
| **Archived** | 永久归档，不参与自动检索 | 手动归档操作 | 无（终态） |
| **Rejected** | L2b 评审未通过 | 评审决策为 rejected | 无（终态） |

### 状态转换审计

每次状态转换记录到资产的变更历史中：

```yaml
state_transitions:
  - from: "candidate"
    to: "active"
    timestamp: "ISO-8601 UTC"
    trigger: "l2d_registration"
    actor: "ai+human"
  - from: "active"
    to: "under_review"
    timestamp: "ISO-8601 UTC"
    trigger: "expiry_reached"
    actor: "system"
```

## 置信度模型

### 设计理念

置信度（confidence）是一个 0.0-1.0 的数值，反映资产在当前时点的可靠程度。它不是静态的标注，而是基于使用反馈动态调整的评分。

### 初始置信度

资产创建时的初始置信度基于来源质量：

| 来源条件 | 初始 confidence | 理由 |
|---------|----------------|------|
| 单次观察，无量化证据 | 0.3-0.5 | 可能是偶然现象 |
| 多次观察（≥2 轮循环），有定性证据 | 0.5-0.7 | 模式初步确认 |
| 量化数据支持（如首通率对比） | 0.7-0.9 | 有统计学支撑 |
| 经专家明确确认且有量化证据 | 0.9-1.0 | 高度可信 |

### 使用反馈机制

每次资产被消费时，根据消费结果调整置信度：

| 事件 | 置信度变化 | 说明 |
|------|-----------|------|
| **使用 + 通过**：引用该资产后，后续 Validate 通过 | **+0.05**（上限 1.0） | 使用成功增强信心 |
| **使用 + 不适用**：引用该资产但发现不适用于当前场景 | **-0.10**（下限 0.0） | 通用性不足 |
| **使用 + 导致偏差**：引用该资产后，后续 Validate 产生偏差 | **-0.15**（下限 0.0） | 准确性存疑 |
| **长期未用**：超过 60 天无引用 | **按类型衰减**（见下方衰减表） | 时间衰减 |

### 置信度阈值

| 阈值 | 触发动作 |
|------|---------|
| **≥ 0.7** | 正常消费，无额外提示 |
| **0.4-0.7** | 消费时显示警告："此资产置信度较低，建议人工确认后使用" |
| **< 0.4** | 触发 Under Review 状态，暂停自动消费 |
| **≤ 0.0** | 自动标记为 Deprecated |

## 衰减/刷新机制

### 时间衰减

不同类型的资产因知识时效性不同，衰减速度不同：

| 资产类型 | 衰减速度 | 理由 |
|---------|---------|------|
| 上下文资产 | 快（-0.03/周未用） | 技术栈和项目架构变化频繁 |
| 意图模式 | 中（-0.02/周未用） | 业务需求演变周期中等 |
| 编排配方 | 中（-0.02/周未用） | Skill 生态和工具链变化 |
| 验证规则 | 慢（-0.01/周未用） | 安全和架构规则相对稳定 |
| 失败案例 | 最慢（-0.005/周未用） | 失败教训通常长期有效 |

### 主动刷新触发条件

除了时间衰减，以下事件触发主动审查：

| 触发事件 | 影响的资产类型 | 审查动作 |
|---------|-------------|---------|
| 技术栈主版本升级 | 上下文资产、编排配方 | 检查版本特定内容是否仍有效 |
| 新安全漏洞公告 | 验证规则 | 检查是否需要新增或修改检查项 |
| 新失败模式发现 | 失败案例 | 检查是否存在关联的已有资产需更新 |
| 业务规则重大变更 | 意图模式 | 检查约束和验收标准模式是否仍适用 |
| 资产被引用时验证失败 | 所有类型 | 立即降低置信度并触发审查 |

### 刷新流程

刷新 = 重新走 L2c（结构化）+ L2d（入库）：
1. 更新内容以反映当前状态
2. 版本号递增（Minor 或 Patch）
3. 重置过期时间
4. 置信度重新评估（不一定恢复到初始值）
5. 记录变更历史

## 版本化管理

### 创建来源追踪

每个资产记录其知识来源，支持事后溯源：

```yaml
provenance:
  source_intent_id: "INT-20260512-003"     # 关联的意图 ID
  source_retro_date: "2026-05-15"          # 来源复盘日期
  source_topic: "intent_quality"           # 来源复盘议题（1-5）
  source_evidence:
    - "3 轮循环中类似意图的 CLEAR 首通率从 40% 提升到 85%"
```

### 变更历史

```yaml
change_history:
  - version: "1.1.0"
    changed_at: "ISO-8601 UTC"
    changed_by: "reviewer_name"
    change_type: "content_update"          # content_update / metadata_update / refresh
    reason: "新增 PostgreSQL 17 兼容性说明"
    diff_summary: "tech_stack.databases 新增 PostgreSQL 17 条目"
```

### 使用记录

```yaml
usage_log:
  total_references: 5
  last_referenced_at: "ISO-8601 UTC"
  reference_outcomes:
    - referenced_at: "ISO-8601 UTC"
      intent_id: "INT-20260520-001"
      outcome: "success"                   # success / not_applicable / caused_deviation
      feedback: "成功应用于类似场景"
```

### 关联关系

```yaml
relationships:
  depends_on:
    - asset_id: "AST-CTX-20260510-001"
      relationship: "此验证规则依赖的上下文定义"
  depended_by:
    - asset_id: "AST-ORC-20260518-002"
      relationship: "此编排配方引用了此资产"
  related:
    - asset_id: "AST-FAI-20260512-001"
      relationship: "同领域的失败案例"
```

## 资产质量评估框架

资产质量通过四个维度定期评估：

| 维度 | 指标 | 计算方法 | 健康标准 |
|------|------|---------|---------|
| **准确性** | 验证通过率 | 使用后 Validate 通过次数 ÷ 总使用次数 | ≥ 80% |
| **时效性** | 距最近更新天数 | 当前日期 - updated_at | < 过期周期的 50% |
| **通用性** | 跨项目适用度 | 不同项目/团队的成功使用次数 | ≥ 2 个不同上下文 |
| **可发现性** | 元数据完整度 | 已填充字段数 ÷ 总字段数 | ≥ 90% |

质量评估结果纳入飞轮指标体系（参见 [飞轮加速度量](./flywheel-metrics.md)），作为资产库健康度的子指标。

**对 SAND 的实践意义：** 资产生命周期管理确保飞轮不会因知识腐化而减速。在非确定性环境中，知识的时效性是一等公民——没有衰减机制的资产库会逐渐积累过时知识，最终比没有资产库更危险（因为团队信任过时的知识而做出错误决策）。置信度模型使"知识的保鲜期"成为可量化、可追踪、可管理的工程概念。
