# 意图类型学

5 种意图类型：Feature（功能）、Fix（修复）、Refactor（重构）、Exploration（探索）、Optimization（优化）。每种类型关联不同的编排拓扑和审查强度。

---

## 概述

意图类型（intent_type）是意图声明的分类标签，影响后续 SDC 循环中的两个关键决策：

1. **编排拓扑选型**：不同类型的意图适合不同的 Agent 协作模式（参见 [编排阶段](../orchestrate/)）
2. **审查强度配置**：不同类型的意图需要不同级别的人类介入（HIP 级别）

分类的目的不是"贴标签"，而是**为编排和验证提供结构化的默认值**——减少 FDE+ 在每次 SDC 循环中需要做的决策数量。

---

## 5 种意图类型

### Feature（功能）

**定义：** 为系统添加全新的功能或能力。

| 属性 | 说明 |
|------|------|
| **典型场景** | 新增 API 端点、新增 UI 页面、新增业务流程 |
| **复杂度特征** | 中到高——涉及设计决策、新增测试、可能的架构影响 |
| **推荐编排拓扑** | Pipeline（多步骤顺序执行）或 Swarm（多 Agent 并行处理不同模块） |
| **推荐 HIP 级别** | HIP-2（关键节点确认）——标准新功能的默认级别 |
| **CLEAR 侧重点** | Complete（功能定义是否完整）、Executable（验收标准是否可执行） |

---

### Fix（修复）

**定义：** 修复系统中不正确的行为——使其恢复到预期状态。

| 属性 | 说明 |
|------|------|
| **典型场景** | Bug 修复、回归修复、异常处理修补 |
| **复杂度特征** | 低到中——问题边界通常明确，修复范围可控 |
| **推荐编排拓扑** | Solo（单 Agent 独立完成） |
| **推荐 HIP 级别** | HIP-1（全自主）或 HIP-2——取决于影响范围 |
| **CLEAR 侧重点** | Assessable（修复效果是否可验证）、Reversible（修复是否可回退） |

**与 Refactor 的边界：** Fix 修复**不正确的行为**（输出错误、异常未处理），Refactor 改善**正确但低质量的实现**（可读性差、性能低、耦合高）。如果当前行为符合预期但代码质量不佳，应选择 Refactor 而非 Fix。

---

### Refactor（重构）

**定义：** 在不改变外部行为的前提下，改善代码的内部结构和质量。

| 属性 | 说明 |
|------|------|
| **典型场景** | 解耦模块、提取通用组件、优化代码结构、减少技术债 |
| **复杂度特征** | 中到高——影响范围可能跨多个文件/模块，需要确保无回归 |
| **推荐编排拓扑** | Pipeline（先分析影响范围，再逐步重构，最后验证） |
| **推荐 HIP 级别** | HIP-2（关键节点确认）——重构的影响范围判断需要人类参与 |
| **CLEAR 侧重点** | Reversible（重构是否可安全回退）、Assessable（行为不变是否可验证） |

---

### Exploration（探索）

**定义：** 验证技术可行性或探索解决方案空间——结果可能是"这条路走不通"。

| 属性 | 说明 |
|------|------|
| **典型场景** | 技术 POC、方案对比评估、性能实验、新库/框架验证 |
| **复杂度特征** | 不确定——探索的本质是发现未知 |
| **推荐编排拓扑** | Solo（快速迭代，单 Agent 独立探索） |
| **推荐 HIP 级别** | HIP-1（全自主）——探索阶段容忍失败，无需严格监督 |
| **CLEAR 侧重点** | Lean（探索范围是否聚焦）、Complete（探索目标是否明确） |

**特殊规则：**
- Exploration 意图的 acceptance_criteria 可以更宽松——"验证 X 方案的可行性并记录发现"是合法的验收标准
- Exploration 的输出通常是一份决策文档（选择 A 还是 B），而非可部署的代码
- **不可将 Exploration 用于需要生产部署的功能**——如果探索结果需要上线，应创建一个新的 Feature 意图

---

### Optimization（优化）

**定义：** 改善系统的非功能特性（性能、可用性、资源利用率等），功能行为不变。

| 属性 | 说明 |
|------|------|
| **典型场景** | 性能调优、缓存策略优化、数据库查询优化、资源消耗降低 |
| **复杂度特征** | 中——需要量化基准和对比测量 |
| **推荐编排拓扑** | Solo 或 Pipeline（先建立基线，再优化，最后对比验证） |
| **推荐 HIP 级别** | HIP-2（关键节点确认）——优化的效果需要人工评估是否满足预期 |
| **CLEAR 侧重点** | Executable（性能基线是否量化定义）、Assessable（优化效果是否可量测） |

---

## 分类汇总

| 类型 | 推荐拓扑 | 推荐 HIP | 核心风险 | CLEAR 侧重 |
|------|---------|---------|---------|-----------|
| Feature | Pipeline / Swarm | HIP-2 | 设计偏差 | C, E |
| Fix | Solo | HIP-1/2 | 回归引入 | A, R |
| Refactor | Pipeline | HIP-2 | 行为变更 | R, A |
| Exploration | Solo | HIP-1 | 范围蔓延 | L, C |
| Optimization | Solo / Pipeline | HIP-2 | 基线缺失 | E, A |

> **注意：** 以上编排拓扑和 HIP 级别为**推荐默认值**，FDE+ 可在编排阶段根据具体情况覆盖。意图类型不硬性绑定拓扑和 HIP——它提供的是起点而非终点。

## 分类判定指南

### 边界情况处理

| 场景 | 推荐分类 | 理由 |
|------|---------|------|
| "修复一个 bug 并顺便优化相关代码" | **Fix** + 独立 **Refactor** | 一个意图一个目的（Lean 原则），应拆分 |
| "探索是否可以用 GraphQL 替换 REST" | **Exploration** | 即使最终会实现，探索阶段的目的是验证可行性 |
| "添加缓存以提升 API 性能" | **Optimization** | 功能不变，改善非功能特性 |
| "添加缓存层 + 基于缓存的新 API" | **Feature** | 新增了功能（新 API），不仅是优化 |
| "迁移数据库从 MySQL 到 PostgreSQL" | **Refactor** | 外部行为不变（API 兼容），内部结构变化 |

### 无法确定类型时

如果意图无法清晰归入单一类型，通常意味着**意图范围过大**——应先使用 [意图分解模式](./decomposition-patterns.md) 拆分，再对每个子意图分别分类。

## 对 SAND Intent Skill 的实践意义

1. **intent_type 在 step-01 确定**：`sand-create-intent` 的 step-01-scope 阶段引导用户选择意图类型
2. **类型决定默认配置**：选定类型后，编排拓扑和 HIP 级别自动填充推荐值（可覆盖）
3. **类型影响 CLEAR 检查权重**：不同类型的 CLEAR 检查侧重点不同，检查报告可据此高亮关键维度
4. **分类统计支撑度量**：intent_type 是 `sand-measure-light` 度量信号之一，用于分析团队的意图组成
