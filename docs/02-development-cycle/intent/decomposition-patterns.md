# 意图分解模式

3 种标准分解模式：垂直切片（用户价值切片）、能力分层（渐进深度）、风险梯度（风险递增排列）。

---

## 概述

当一个意图的范围过大——无法在单个 SDC 循环内完成，或 CLEAR 检查的 Lean 维度提示需要拆分——就需要将其分解为多个子意图。意图分解不是随意拆分，而是遵循结构化的模式来确保拆分后的子意图**各自独立交付价值且总体完整**。

### 何时拆分

| 信号 | 说明 |
|------|------|
| **CLEAR L4 不通过** | 范围超出单个 SDC 循环的合理时长 |
| **acceptance_criteria > 10 条** | 验收标准过多，通常意味着多个关注点混合 |
| **constraints 存在矛盾** | 不同部分的约束互相冲突，说明是不同的问题域 |
| **intent_type 无法确定** | 一个意图同时具有 Feature 和 Refactor 的特征 |
| **多个独立的 desired_outcome** | "成功"需要多个不相关的状态变化同时发生 |

---

## 模式 1：垂直切片（Vertical Slice）

### 定义

按**用户价值端到端切片**——每个子意图独立交付一个完整的用户可感知价值，从 UI 到数据层贯穿所有技术层级。

### 适用场景

- Feature 类型意图，涉及多个用户故事
- 需要渐进交付的大功能
- 每个切片可独立上线、独立验证

### 操作步骤

1. 识别原始意图中的独立用户价值单元
2. 每个价值单元成为一个子意图，包含完整的 7 字段
3. 子意图之间通过 `context_references.related_intents` 关联
4. 为子意图排定执行顺序（通常按业务价值或技术依赖）

### 示例

**原始意图：** "实现多租户权限隔离系统"

**分解为：**
- 子意图 A（Feature）：租户数据 API 隔离——API 请求仅返回当前租户数据
- 子意图 B（Feature）：跨租户访问审计——非法访问尝试记录审计事件
- 子意图 C（Optimization）：隔离性能优化——确保隔离逻辑不显著降低 API 性能

### 与意图类型的对应

垂直切片最适合 **Feature** 类型——每个切片是一个可独立交付的功能单元。

## 模式 2：能力分层（Capability Layering）

### 定义

按**技术深度渐进实现**——先实现基础能力，再逐步增强。每一层建立在前一层之上，但前一层可以独立使用。

### 适用场景

- Refactor 或 Feature 类型意图，涉及多个技术层级
- 需要先建基础设施再构建上层功能
- 前一层的稳定性对后续层至关重要

### 操作步骤

1. 识别技术能力的层级关系（基础 → 增强 → 高级）
2. 每层成为一个子意图，后层在 `context_references.related_intents` 中引用前层
3. 严格按层序执行——前层必须 Validated 后才启动后层
4. 每层的 acceptance_criteria 独立于后层（不依赖后层才能验证）

### 示例

**原始意图：** "建立 AI 辅助代码审查系统"

**分解为：**
- 层 1（Feature）：静态分析集成——接入现有 lint 工具，输出结构化审查建议
- 层 2（Feature）：AI 审查建议——基于 LLM 生成代码审查意见
- 层 3（Optimization）：审查优先级排序——根据变更风险自动排序审查建议

### 与意图类型的对应

能力分层适合 **Feature** 和 **Refactor** 类型——技术层级关系明确的场景。

---

## 模式 3：风险梯度（Risk Gradient）

### 定义

按**风险从低到高排列**——先验证低风险假设，再处理高风险部分。失败成本递增，每一步的成功为下一步建立信心。

### 适用场景

- Exploration 类型意图，技术可行性不确定
- 涉及不可逆操作（数据迁移、架构变更）
- 失败代价高，需要渐进式验证

### 操作步骤

1. 列出原始意图中的所有风险假设
2. 按风险影响 × 不确定性排序（低→高）
3. 每个风险假设成为一个子意图（通常是 Exploration 类型）
4. 低风险子意图先执行，其结果决定是否继续高风险子意图
5. 高风险子意图的 constraints 中包含回退策略

### 示例

**原始意图：** "从 MySQL 迁移到 PostgreSQL"

**分解为：**
- 子意图 A（Exploration）：兼容性验证——在测试环境验证 SQL 兼容性和 ORM 适配
- 子意图 B（Feature）：双写机制——实现 MySQL + PostgreSQL 双写，验证数据一致性
- 子意图 C（Refactor）：切换主库——将读写切换到 PostgreSQL，MySQL 降级为备份
- 子意图 D（Fix）：清理——移除 MySQL 相关代码和配置

### 与意图类型的对应

风险梯度适合**混合类型**场景——子意图的类型可能各不相同（Exploration → Feature → Refactor → Fix），体现了风险递进的过程。

## 拆分后的依赖管理

### 子意图间的关系类型

| 关系 | 说明 | 管理方式 |
|------|------|---------|
| **顺序依赖** | B 必须等 A 完成才能开始 | A 的 intent_id 写入 B 的 `context_references.related_intents`，B 的 constraints 中注明"依赖 A 的输出" |
| **并行独立** | A 和 B 可同时执行 | 两者通过 `related_intents` 互相引用，但无执行顺序约束 |
| **条件依赖** | B 是否执行取决于 A 的结果 | A 的 desired_outcome 中定义决策条件，B 的 constraints 中注明前置条件 |

### 总体完整性验证

拆分后必须验证：所有子意图的 acceptance_criteria 的**并集**覆盖原始意图的全部 acceptance_criteria。如果存在遗漏，说明拆分不完整。

---

## 对 SAND Intent Skill 的实践意义

1. **CLEAR L4 是分解触发器**：当 Lean 维度的 L4 检查不通过时，`sand-create-intent` 应引导用户选择分解模式
2. **分解模式选择可推荐**：根据 intent_type 推荐默认分解模式——Feature → 垂直切片，Exploration → 风险梯度，Refactor → 能力分层
3. **子意图自动关联**：分解后的子意图通过 `context_references.related_intents` 自动建立关联，供编排阶段使用
4. **分解是递归的**：子意图如果仍然过大，可以再次分解——但通常不建议超过 2 层分解深度
